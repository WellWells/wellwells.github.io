用 LLM 把 Perplexity 搜尋結果、YouTube 字幕或 PDF 整理成 TailwindCSS 單頁網頁，再用 GitHub Actions 從私人儲存庫自動部署到 GitHub Pages，附完整的 workflow 腳本。

前言

我們每天從網路上擷取、學習各式各樣的內容，看 YouTube 學習相機設定、查除濕機原理、比較舒肥機哪台最好、追蹤 iOS 的新功能，或規劃日本自助行。問題是這些內容多半沒被記錄下來，看過就忘，30 分鐘的影片看完也常常抓不到重點。

AI 摘要工具、主動筆記法和分段觀看策略都能改善這件事。先前曾分享過的文章 《透過 ChatGPT 進行 YouTube 影片分析與總結》能夠快速取得影片的文字稿、或是《使用 Faster Whisper 取得任何影片或音訊的原始字幕》能夠將純影片的內容轉換為文字稿。

後續交給大型語言模型（large language model，LLM），如 OpenAI ChatGPT、Google Gemini、Anthropic Claude 等工具做摘要、分類與重組；最後把結果儲存在 Notion 供應個人閱讀或私人分享。

也可以直接轉成能上線的單頁網站（single-page site）。這篇文章說明一套完整的自動化流程，從用 AI 統整內容、產生網頁原始碼，到用 GitHub Actions 自動部署網站。沒有深厚程式背景的人也能自己建置、發布網頁，把看到的文章快速分享出去。

運用 LLM 進行內容統整或產生可靠性的內容

目前市場上有許多 AI 工具可以協助內容統整與產生，如 ChatGPT、Gemini 等。這些工具支援多元化的輸入來源，包括：

  • 完整文章內容
  • YouTube 影片字幕
  • PDF 檔案
  • 網路搜尋統整結果

以我常用的搜尋統整結果為例子：

1. Perplexity

  • 整合多個網頁來源做綜合分析。
  • 適合需要多角度資訊統整的研究需求。
  • 附上來源引用與連結，便於回溯與驗證。

2. Gemini Deep Research

  • 自動化網路資訊瀏覽與分析。
  • 快速產出綜合性研究報告（數分鐘內完成）。
  • 專門處理複雜的研究任務。

使用 GitHub Pages 部署靜態 HTML 網站

GitHub Pages 很方便，可以直接從 GitHub 儲存庫（Repository）託管靜態網站。這份教學會帶你把一個簡單的 HTML 檔案部署上線。

前置準備

在開始之前，請先確認你已經：

  1. 擁有一個 GitHub 帳號。
  2. 在自己的電腦上安裝了 Git。
  3. 對 Git 的基本操作有初步了解，例如 clone, add, commit, push。

若對 Git 不熟悉，可以參考以下文章：

  • 《Git 基礎教學：什麼是版本控制？核心概念與遠端儲存庫介紹》
  • 《Git 基礎教學：使用 VS Code 推送程式碼至遠端儲存庫》

上傳網頁

首先，在 GitHub 上建立一個新的公開儲存庫，例如 single-page-conclusion。

假設有一個名為 Git 常見指令統整.html 的檔案。使用 Git 指令將本地的專案提交至專門的分支 gh-pages，並將該分支推送上去。

接著就可以在 https://<你的使用者名稱>.github.io/<你的儲存庫名稱>/Git 常見指令統整.html 這個網址看到網頁內容。

使用 GitHub Actions 實現自動化部署

有些腳本或設定不希望公開，所以原始碼放在私人儲存庫，只把最終產出的網頁檔案部署到公開儲存庫。這一段交給 GitHub Actions，程式碼推上私有儲存庫後，它會自動跑預設好的指令，把網頁檔案發布到公開儲存庫。

為了清楚說明，以下假設有兩個 GitHub 儲存庫：

  • 私人儲存庫 (Private Repository): single-page-conclusion-deploy
    • 存放所有原始碼、腳本 (.sh) 與提示詞 (.txt)，這是主要的工作區。
  • 公開儲存庫 (Public Repository): single-page-conclusion
    • 僅用於存放最終產生的靜態 HTML 檔案，並啟用 GitHub Pages 功能來發布網站。

建立與使用個人存取權杖

要讓私有儲存庫的 Actions 有權限自動推送到公開儲存庫，必須建立一把金鑰來做認證。最常見的做法是使用個人存取權杖（personal access token，PAT）。

  1. 產生 PAT

    到 GitHub 的 Personal Access Tokens 頁面，點選 Generate new token，並選擇 Generate new token (classic) 來產生新的金鑰。

  2. 設定 Token Scope

    在 Select scopes 中，務必勾選 repo、workflow 的所有權限。這把金鑰才有辦法對你的儲存庫做讀取、寫入等操作。

  3. 儲存金鑰為 Secret

    產生金鑰後，請立即複製它。它會是一長串以 ghp_ 開頭的字元，例如：

    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

  4. 新增 Secret 至私人儲存庫

    前往私人儲存庫 (single-page-conclusion-deploy)，進入 Settings > Secrets and variables > Actions，點選 New repository secret。將金鑰命名為 GH_TOKEN 並貼上內容。

    完成設定後，Workflow 就能用 ${{ secrets.GH_TOKEN }} 安全地讀取這個金鑰，取得推送到公開儲存庫的權限。

撰寫 Workflow 部署腳本

以我個人的目錄架構為例，以下檔案皆在我的私人儲存庫中管理：

  1. ./提示詞.txt
  2. ./update_rss.sh
  3. ./update.sh
  4. ./gh-pages/*.html

其中，前三項是我個人使用的腳本與資料，而真正需要部署上線的，只有 ./gh-pages/ 目錄下的靜態網頁檔案。

# .github/workflows/deploy.yml

# name: 為此工作流程設定一個在 GitHub Actions 介面上顯示的名稱。
name: Deploy HTML to single-page-conclusion

# on: 定義觸發此工作流程的事件。
on:
  # push: 當有 Git push 事件發生時觸發。
  push:
    # branches: 指定只有推送到特定分支時才會觸發。
    branches:
      # 當私有儲存庫的 'main' 分支有任何更新推送時，此工作流程就會啟動。
      - main

# jobs: 工作流程由一或多個「工作（Job）」組成，它們可以依序執行。
jobs:
  deploy:
    # 指定此工作在最新的 Ubuntu 系統上執行
    runs-on: ubuntu-latest

    # steps: 「工作」是由一系列依序執行的「步驟（Step）」所組成。
    steps:
      # 步驟一：簽出（Checkout）私有儲存庫的程式碼
      - name: Checkout private repo
        # uses: 使用 GitHub Marketplace 中預先寫好的 Action。
        # actions/checkout@v3: 這是官方提供的 Action，功能是將觸發此流程的儲存庫程式碼下載到 Runner 中。
        uses: actions/checkout@v3
        # with: 為使用的 Action 傳入特定參數。
        with:
          # fetch-depth: 0: 拉取完整的 Git 歷史紀錄。這在需要基於 Git 歷史進行操作時很有用。
          fetch-depth: 0

      # 步驟二：設定 Git 提交者資訊
      - name: Setup Git
        # run: 直接在 Runner 的 shell 環境中執行指令。
        run: |
          git config --global user.name "github-actions[bot]"
          git config --global user.email "41898282+github-actions[bot]@users.noreply.github.com"

      # 步驟三：執行腳本以產生 README.md
      - name: Generate README.md
        run: |
          chmod +x update.sh
          ./update.sh

      # 步驟四：複製（Clone）公開的目標儲存庫
      - name: Clone public repo (single-page-conclusion)
        run: |
          # 透過金鑰，把公開儲存庫複製到本機中的 public-repo 目錄。
          # 這個金鑰需要預先在私有儲存庫的 Settings > Secrets 中設定。
          git clone --depth 1 https://x-access-token:${{ secrets.GH_TOKEN }}@github.com/<USER>/<PUBLIC_REPO_NAME>.git public-repo
          
          # 進入剛剛 clone 下來的 'public-repo' 資料夾。
          cd public-repo
          
          # 以下指令確保不論遠端分支是否存在，都能順利切換，避免因分支不存在而導致 workflow 失敗。
          # || true: 如果前面的指令失敗（例如遠端沒有 main 分支），則回傳成功狀態，讓 workflow 繼續執行。
          git fetch origin main || true
          git fetch origin gh-pages || true
          
          # 嘗試切換到 main 分支，如果不存在，就建立一個新的 main 分支。
          git checkout main || git checkout -b main

      # 步驟五：同步檔案至公開儲存庫的 main 分支（主要更新 README）
      - name: Sync files to public repo main
        run: |
          cd public-repo
          # 將上一步驟在私有儲存庫根目錄產生的 README.md 複製到公開儲存庫的資料夾中。
          cp ../README.md .
          
          # 將 README.md 加入 Git 的暫存區。
          git add README.md
          # 提交變更。如果沒有任何變更（檔案內容和上次一樣），commit 會失敗。
          git commit -m "Update README.md" || echo "No changes"
          # 將 commit 推送到公開儲存庫的 main 分支。
          git push origin main

      # 步驟六：同步網站內容至公開儲存庫的 gh-pages 分支（部署網站）
      - name: Sync files to public repo gh-pages
        run: |
          cd public-repo
          # 切換到 gh-pages 分支，這是 GitHub Pages 用來發布網站的預設分支。如果不存在則建立。
          git checkout gh-pages || git checkout -b gh-pages

          # --- 清理舊檔案 ---
          # 為了確保部署的內容是最新的，先刪除上次部署的檔案。
          # 這可以避免舊的、已在來源中刪除的檔案殘留在遠端上。
          find . -maxdepth 1 -name '*.html' -delete
          rm -f README.md
          
          # --- 複製新檔案 ---
          # 將私有儲存庫中 'gh-pages' 資料夾內的所有新檔案複製過來。
          # 這些是網站的實際內容。
          cp ../gh-pages/*.html .
          cp ../README.md .
          
          # --- 提交與推送 ---
          # 將所有新增、修改、刪除的檔案加入 Git 暫存區。
          git add .
          # 提交所有變更。
          git commit -m "Update content, RSS feed and posts data" || echo "No changes"
          # 強制推送（force push）到 gh-pages 分支。
          # --force: 使用強制推送確保遠端分支的內容與此次部署完全一致，覆蓋掉舊的歷史紀錄。
          # 這在自動化部署 gh-pages 這類分支時是常見且安全的做法。
          git push origin gh-pages --force

儲存後提交、推送到伺服器上後，每當更新推送到私有儲存庫的 main 分支，GitHub Actions 就會自動執行上述步驟（更新 README.md 並部署最新的靜態網頁）。基於同樣的邏輯，也可以輕易擴充此流程，例如加入自動產生 rss.xml 的步驟。

這個方法既能保有原始碼與腳本的隱私，公開儲存庫裡也只會留下乾淨、可以直接發布的內容。

結論

這篇走完了一套從內容統整到網站自動發布的流程。把 LLM 的內容處理能力接上 GitHub Actions 的自動化部署，繁瑣的發布動作最後就簡化成一次 git push。

相較於把筆記留在私人空間，整理成獨立網頁之後，自己的理解會紮實一點，別人也找得到。
