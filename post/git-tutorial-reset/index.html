前言

在前篇文章：Git 進階教學：在 VS Code 處理變基與分支合併，已經談過如何用變基（rebase）重新編排、修改和移除提交。

變基可以一次把提交壓縮（squash）、改寫（reword）、刪除（drop），讓分支的歷史保持乾淨。

本篇文章要說明的回退（reset），可以在不更動檔案的情況下，使 HEAD 跳到所指定的提交上，做更細微的分支、提交操作。

範例分支狀態

  1. （0b33..b535）新增 A.txt, B.txt, C.jpg 並各自獨立提交。
  2. （0a573c34）然後同時修改 A.txt, B.txt 兩個檔案，並新增 FIX 字串，提交兩個檔案。
  3. （32e8ea75）最後又修改 A.txt，新增 FIX A2 字串在 A.txt 檔案內後再次提交。

如果要把所有的 A.txt 修改合併為一個提交，且與 B.txt 的修改獨立開來，可以用回退把提交拆開。

再結合變基、挑選（cherry-pick），就能做更複雜、更細微的調整。

回退的三種模式

⚠️ 在做以下操作前，請先確認所有變更已經提交至儲存庫，並且沒有任何暫存的內容。

git reset --mixed

在最後一個提交上新增一個 mixed 分支來說明，可以看到目前 HEAD 指向 32e8ea75。

對著提交右鍵點選 Reset current branch to this Commit... (將目前分支回退至此提交...)。

可以再不改變目前所有檔案情況下，重新定位 HEAD 指標至所選定的提交。

可以看到的是，回退到先前提交，由於工作目錄下的檔案與目前 HEAD 所指向的提交不一致，所以檔案差異會變為變更狀態。

git reset --soft

在最後一個提交上新增一個 soft 分支來說明。

與 git reset --mixed 不同的是，回退後檔案會放在暫存區，等待再次提交。

如果 Unstage（git reset）把暫存中的變更回退到工作目錄，會發現與 git reset --mixed 一樣。

git reset --hard

這個最好理解，就是拋棄當下所有變更，直接把 HEAD 移動到指定的提交。

⚠️ 注意，會連同暫存區一併清空。所以在操作前，請記得保存當下的狀態。

透過 reflog 復原失敗的操作

如果在回退操作中未事先建立新的分支來保存目前的提交點，則原先的提交會變為孤立提交（orphan commit）。孤立提交是指不再由任何分支指向的提交，這可能導致這些提交在未來的垃圾回收中被刪除。

這種情況可以用 git reflog 列出所有 git 操作過的紀錄，從裡面找回這些孤立提交。如果要查看 log 操作的精確時間，可以加上 --date=iso 選項。如果想簡要顯示每次提交的內容，則可以使用 --pretty=short 選項，或是用重新導向輸出成一個檔案。

透過回退進行複雜的合併

有時候在整理提交，會發現提交中含有多個檔案，如果要一次性的合併，該如何進行？

例如以下分支：Node → 提交 A 檔案 → 提交 B 檔案 → 提交 C 檔案 → 同時提交 A, B 檔案 → 更新 A 檔案

在最後一筆更新 A 檔案上，已經確定完善且不需要先前所有 A 的提交，用回退可以很快把提交裡的檔案整合、分離。

目標為：Node → 提交 A 檔案_withFixed → 提交 B 檔案_withFixed → 提交 C 檔案。

其中，可以在最後一筆直接回退至 Node 後，一筆一筆重新提交，但所有提交時間都會遺失。

若要盡量保留提交時間、作者等資訊，可以用兩個分支加上變基來做，其流程如下：

  1. 於最後一筆提交新增 test 分支，並切至該分支。
  2. mixed 回退至預期想要的節點，此時會保留工作區的狀態、但是 HEAD 回退了。
  3. 將不需要的檔案移除，如 B, C 檔案。
  4. 重新提交 A 檔案，這個 A 檔案已經包含 Fix 等相關修正。
  5. 切至new_merge分支。
  6. 對著Merge_A右鍵變基，途中遇到衝突，由於 A 檔案已包含修改，所以遇到的衝突要選擇保留本地端的狀態。
  7. 變基後，用 git diff 比對 new_merge 分支與 master 分支的差異。如果沒差異則不會輸出東西，代表 new_merge 與 master 是一致的。
  8. 如果還要再調整，將 test 分支 hard 回退到 new_merge 上，重新做步驟 2 ~ 7。
  9. （有需要的話）刪除 master 分支，將 new_merge 分支改名 master 後推送。推送後，其他人會因為找不到原本的父節點而發生衝突，此時其他人的修改需要變基到新的 master 分支上才能再次推送。這邊需要協調好團隊之間的行為。

我個人會更傾向於使用兩個分支 + 回退 + 變基的操作。如果過程中遇到錯誤，不知道怎麼解決衝突，都可以用 git rebase --abort 隨時終止變基。

總結

使用回退可以任意將 HEAD 指向某個特定的提交，不同模式之間有細微差異。

  1. mixed 會保留目前工作目錄下的檔案，移動 HEAD
  2. soft 會保留目前工作目錄下的檔案，並且放置暫存區後，移動 HEAD
  3. hard 會拋棄目前工作目錄下的所有檔案，將 HEAD 移動到指定的提交。

進階的合併操作，可以用兩個分支加上回退、變基來完成。

或是單純使用變基，在變基過程中用 edit 中斷，回退拆開提交、再次提交，然後繼續變基。
