Deno 加入 Cloudflare，runtime 一年後停止官方開發

Deno 加入 Cloudflare 的公告重點：runtime 再維護一年、Deno Deploy 六個月後關閉、celld 併入 workerd，以及我遷回 Node.js 的原因。

2026 年 10 月 9 日，Deno 創辦人 Ryan Dahl 在 Deno 官方部落格宣布整個 Deno 團隊加入 Cloudflare。Deno 團隊會再支援 Deno 的 JavaScript runtime 一年，之後結束自己的開發，專案維持開源。我已經把用 Deno 開發的專案遷回 Node.js，看到公告時沒有太意外，但還是把官方說法、Cloudflare 的動機和各家 runtime 的現況查了一輪，整理如下。

公告說了什麼

Cloudflare 同一天也發了一篇由 Ryan 與 Kenton Varda 共同署名的文章，內容是 workerd 與 celld 合併，沒有交代 Deno runtime 的去向，要看 Deno 那篇才知道。

項目公告內容
Deno runtime再支援一年，每月釋出 bug fix 與安全性更新，之後 Deno 團隊結束自己的開發；專案維持開源，歡迎其他人接手
Deno Deploy繼續運作六個月後關閉；付費客戶遷移到 Cloudflare Workers 時提供遷移支援
JSR繼續運作，基礎設施移到 Cloudflare
rusty_v8持續維護，並朝整合進 workerd 的方向進行
Fresh、Deno Subhosting公告沒有提到

Deno Deploy 的六個月從何時起算，公告沒有說，從 10 月 9 日起算大約是 2027 年 4 月。

Cloudflare 要的是 celld

celld 是 Deno 團隊 2026 年 8 月釋出的開源專案，以 Rust 寫成的單一執行檔，授權是 Apache-2.0。用現有的 wrangler.json 就能把 Cloudflare Workers 應用連同 Durable Objects 跑在自己的機器上，需要 Cloudflare 網路、GPU 或瀏覽器農場的產品不在支援範圍內。

Durable Objects 是 Cloudflare 把運算和儲存綁在一起的 Worker，每個物件有全域唯一的名稱和私有的儲存空間，單執行緒運作。Cloudflare 開源的 Workers runtime 是 workerd，但 Kenton 寫到 workerd 的 Durable Objects 只有單一實例的實作，"good enough for local testing, but unable to scale"。Cloudflare 因此計畫把 celld 的程式碼與想法併回 workerd，由 Ryan 和 Bert Belder 主導，讓 workerd 自行架設成為正式支援的方式。

Deno 的公告另外提到，Durable Objects 的持久狀態與 WebSocket 很適合 agent harness，這也是 celld 聚焦 Durable Objects 的原因。

近一年加入大公司的開發工具

Bun 在 2025 年 12 月加入 Anthropic，聲明維持開源與 MIT 授權，Claude Code 本身就是以 Bun 執行檔發行。開發 uv 與 Ruff 的 Astral 在 2026 年 3 月 19 日宣布與 OpenAI 達成協議，將加入 Codex 團隊；交易當時尚未完成，我也沒有查到完成的消息。Astro 在 2026 年 1 月加入 Cloudflare，同樣維持 MIT 授權。這幾個案例都說會繼續開發，Deno runtime 是這批裡唯一明講結束開發的。

下游也受影響。Supabase 的文件寫 Edge Functions 以 Deno 開發，Netlify 的文件寫 Edge Functions 跑在以 Deno 為基礎的 runtime 上。截至 10 月 10 日，我沒有找到這兩家對公告的官方回應。

Deno 做對的事

Deno 由 Node.js 的原作者 Ryan 創辦，主打預設沙箱和不需額外工具就能執行 TypeScript。下面幾項是我認為 Deno 做得比較早的地方，Node.js 後來也陸續提供了對應功能，但成熟度不一。下表是 2026 年 10 月 10 日的狀態：

功能DenoNode.js
原生 TypeScript內建預設啟用且已穩定，只移除型別，不做型別檢查
內建測試工具Deno.testnode:test，已穩定
編譯成單一執行檔deno compileSingle executable applications，Stability 1.1，積極開發中
權限控管預設沙箱--permission 已穩定，需要主動開啟

deno compile 這一項差距最明顯：Node.js 官方文件還把單一執行檔列在積極開發中，Deno 已經是一般的 CLI 指令。這幾項讓專案少掉打包工具和測試框架的依賴，是我對 Deno 評價最高的部分。

官方說歡迎其他人接手，但維護一整套 runtime 的工作量很大，我不預期短期內會有實質的接手者。Anthropic 收購 Bun，OpenAI 說不定哪天會接手 Deno，不過這純屬我的猜測。

我遷回 Node.js 的原因

我在《2024 年終回顧》提到，2024 年底決定把個人專案的技術堆疊換成 Deno、PostgreSQL 與 Next.js。實際開發時遇到一堆相容性問題，這些問題在 Node.js 上不會發生，兩個代表性的例子我寫在《實戰 Agentic Workflow》。Electron 深度綁定 Node.js，搭配 Deno 的開發體驗欠佳；改用 Tauri 又得先建置 Rust 開發環境。遷回 Node.js 之後，維護至今沒有遇到阻礙。

Deno 的 npm 相容要到 2022 年 11 月的 1.28 才穩定，2024 年 10 月的 Deno 2 才進一步原生支援 package.json 與 node_modules。Next.js 也有落差，Deno 官方的 Next.js 教學需要在 deno.json 開啟四項 unstable 設定；桌面應用的 deno desktop 則到 2026 年 6 月的 Deno 2.9 才以實驗性功能加入。

Bun 換語言的風險

Bun 原本以 Zig 開發。2026 年 5 月 14 日，把 Zig 程式碼全部改寫成 Rust 的 PR 合併，v1.4.0 在 8 月 20 日成為第一個 Rust 版本。Bun 說明的原因是 v1.3.14 的修正清單中，有很大比例是 use-after-free 與 double-free 這類記憶體錯誤，根源在垃圾回收與手動記憶體管理混用；作者 Jarred Sumner 也說 "I don't blame Zig for that"。

改寫的範圍是所有 Zig 程式碼，約 20% 的 C++ 程式碼與 JavaScriptCore 等函式庫仍然保留。對 production 來說，底層語言整個更換本身就是風險，Bun 自己承認這次改寫引入了 19 個已知 regression，且都已修正。

Bun 在 2025 年 12 月的加入公告中說明，Anthropic 把它當成 Claude Code 與 Agent SDK 的基礎設施，並已連續數個月優先處理 Claude Code 團隊提出的 issue。路線圖則說會繼續聚焦在高效能 JavaScript 工具與 Node.js 相容性。通用路線是否因此偏離，目前沒有證據，我只把它列為評估風險的項目。

選型的依據

在 production 我選 Node.js，依據是 State of JS 問卷的作答人數和 Node.js 的發版規則。State of JS 2025 的 runtime 項目基數是 11,141 人，Node.js 有 10,062 人，占 90.3%。兩年的基數不同，下表用占比比較 Deno 與 Bun：

年度基數Deno 人數Deno 占比Bun 人數Bun 占比
202411,5761,36511.8%1,89416.4%
202511,1411,24411.2%2,32120.8%

Node.js 的長期支援版本（LTS）通常保證共 30 個月內修復重大 bug，官方建議 production 應用只使用 Active LTS 或 Maintenance LTS。截至 10 月 10 日，v24 是 Active LTS，v22 是 Maintenance LTS。官方也預定從 27.x 起改成每年一個主版本，且每個主版本都會進入 LTS，這份時程尚未定案，但照目前規劃可以提前排升版時程。

已經在用 Deno 的專案還有一年的每月更新，足夠規劃遷移；我自己的專案維持在 Node.js 上。
