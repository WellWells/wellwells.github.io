Git 進階教學：在 VS Code 處理變基與分支合併

在 VS Code 做 Git 變基與分支合併：互動式變基的 squash、reword、edit，怎麼把一筆提交拆開，以及用 Force With Lease 安全推送。

前言

在前篇文章中介紹了 Git 基礎教學：使用 VS Code 建立、切換與刪除分支。

本篇的重點是在 VS Code 用變基（rebase）整理提交，以及分支合併（merge）的操作流程。

範例情境

⚠️ 在做以下操作前，請先確認所有變更已經提交至儲存庫，並且沒有任何暫存的內容。

合併

從遠端儲存庫複製到本機後，若想要開發新功能，會建立一個新分支再繼續提交。

例如，假設目前的主分支為 main（或 master），想開發新的演算法功能。這個新功能會基於目前已提交的內容開發，所以可以建立一個新分支（例如：feature/alg_dev）。

演算法開發完成後，把 feature/alg_dev 分支合併到 main 分支上，再推送。

（也可以用變基把 feature/alg_dev 的提交移動到 main 上後推送。或是切換到 main 分支，cherry-pick 後推送。）

變基

在目前分支中，可以選擇某個提交作為起點，並對後續所有提交進行修改。

例如：目前正在某個提交（Node）上開發：Node → 提交 A → 提交 B (feature/alg_dev)

然後發現遠端有了新的提交：Node → 提交 1 → 提交 2 (main)

這時可以變基，方法為切換到 feature/alg_dev 分支，並以提交 2為起點，這樣就會變成：Node → 提交 1 → 提交 2 → 提交 A → 提交 B，完成功能的整合。

另一種情境為：Node → 提交 A1 → 提交 A2 → 不需要的測試 C → 提交 B1 → 提交 B2

用互動式變基（interactive rebase），可以任意排序提交順序、壓縮（squash）、刪除（drop）、修改（edit）或改寫（reword）提交。

並將其提交壓縮，整理為：Node → 提交 A → 提交 B

目前的分支狀態

每個人的分支狀態不一樣，在此接續先前文章 Git 基礎教學：結合 VS Code 圖形化介面輕鬆搞定版本控制 所建立的測試 Git repo 來操作。

也建議先從簡單的儲存庫開始，大約半天的時間就可以摸熟整個流程。

修改 Git 預設編輯器

用 Remote SSH 連到 Linux 上操作 Git 時，所使用的編輯器可能是 vim 或是 nano，可以用以下指令把 Git 的編輯器改為 VS Code：

1

git config --global core.editor "code --wait"

Windows 下預設應該是 VS Code，如果不是也可以執行上方的指令修改。

合併（merge）

合併分支是將一個分支的更改整合到另一個分支的過程。它會建立一個特殊的合併提交，記錄了兩個分支的差異。

其中需要注意的是：

  1. 合併衝突：不同分支修改了同一個檔案的同一部分時，合併可能會產生衝突。解決衝突需要手動選擇要保留哪些更改。這需要對原始內容有一定的熟悉程度才知道該如何解決衝突。
  2. 歷史保留：合併會保留分支的歷史。如果每次開發一個新功能都是使用合併分支的行為，會造成歷史紀錄太多且複雜，需要有人重整歷史紀錄。

合併分支

合併分支很簡單，目前 master 的 SHA 為 f2654174，切到 master 分支上，對分支 feature 右鍵點選Merge into current branch。

此時會跳出三個選項，分別為：

  1. Create a new commit even if fast-forward is possible

    快轉（fast-forward）會發生在分支為直線的情況，勾選則表示合併分支會額外建立一個新的提交（f68077d6），不勾選的話，由於 feature 對 master 是直線，所以會直接把 master 的 HEAD 直接移動到 9dcb1afa。

    如果切換到 feature2 分支，並想要合併 feature 的分支，由於他們並非直線，所以這個選項有勾沒勾都會是同樣的結果，都會建立一個新的合併提交。

  2. Squash Commits（壓縮提交）

    會先壓縮再提交，所以 bf2a6b87 與 9dcb1afa 會被壓縮後，建立一筆新的提交。

  3. No Commit

    會把 feature 分支上的提交壓縮後，儲存在暫存區中，不會建立新的提交。

變基（rebase）

變基是將一個分支的更改重新應用到另一個分支上。這種方法可以創造一個更線性、乾淨的提交歷史紀錄。

其中需要注意的是：

  1. 操作前建議切換到暫時分支：變基前建議開新的暫時分支來操作，有任何操作失誤，想復原都可以隨時中止並還原到原始狀態。
  2. ⚠️變更歷史紀錄：變基會修改歷史紀錄，在多人合作的專案中，因為變基後的分支推送到遠端儲存庫時，會導致與其他貢獻者的歷史與遠端不一致，因此產生衝突。
  3. 衝突處理：由於修改了歷史紀錄，擷取、提交或推送時會遇到衝突。
  4. 變基有兩種：一種是標準變基（standard rebase）與互動式變基（interactive rebase），對於初學者和進階使用者而言，互動式變基有更多的控制選項和彈性。除非你對目前分支的狀態和手上的操作有充分的了解，否則建議優先考慮使用互動式變基。

互動式變基

互動式變基時，會選擇一個特定的提交作為起點，並基於這個起點調整後續的提交。以下是互動式變基過程中可以對提交做的操作：

  • pick：選擇此提交並保持原樣，不做任何修改。
  • reword：僅修改此提交的訊息，不改動任何檔案內容。
  • edit：在此處暫停變基過程，可以修改提交本身，比如更改檔案內容或者提交訊息。
  • squash：將此提交與前一個提交合併，同時合併兩個提交的訊息。
  • fixup：功能與 squash 相似，但會丟棄此提交的訊息，只保留前一個提交的訊息。（這個基本上不會使用到。）
  • drop：放棄此提交，將其從提交歷史中完全刪除。

選擇（Pick）

把 feature2 的修改，變基到 feature 上。

先切換到 feature2 的分支（在此預防操作失誤，開了新的分支: merge_all），然後以 feature 上的最後一筆提交作為起點變基，在此只做 pick。

反之，把 feature 的修改變基到 feature2 上。

切換到 feature 分支，並對著 feature2 變基。

會把 feature 上的 [新增] 您好.txt 與 [新增] 您好2.txt 提交，附加在 [New] 新增第三行內容 後。同理，如果變基過程中有不要的提交，就把 pick 改為 drop 即可。

壓縮提交（Squash）

把 feature 的修改合併到 feature2 上，如果想要壓縮多個提交，就選壓縮提交。變基過程中會要求輸入提交訊息。

修改提交訊息（reword）

把 feature 的修改合併到 feature2 上，並且修改特定提交的內容，但不想合併，可以選擇 reword。變基過程中會要求輸入提交內容。

編輯提交內容（edit）

最後是變基的編輯（edit）。假設當初提交時一次塞了一坨檔案，但這個提交內的檔案應該要拆成獨立的提交，可以用變基（rebase）→重置（reset）→提交（commit）把檔案拆開。編輯提交內容也可以單純只改訊息，不更動檔案，或者做其他操作，如挑選（cherry-pick）、新增檔案等等。

以範例來說，可以看到[新增] 一坨.txt這個提交有兩個檔案變更，目的是把這兩個檔案變更拆解為兩個獨立提交。

在該提交的上一筆變基，並在提交面板中選擇 edit 後，會進入分離指標狀態，此時的 HEAD 仍然指向[新增] 一坨.txt。

接著要復原上一個提交（git reset HEAD~1）。這會將 HEAD 退回上一個提交，也就是 [New] 新增第三行內容，並且 [新增] 一坨.txt 原先內的檔案會變為暫存狀態（stage）。

將檔案全部取消暫存（unstage all changes）後會變為變更狀態（modified），這邊可以選擇性地重新把它們加入暫存區。由於 VS Code 的限制，在變基狀態下沒辦法用 UI 提交，所以只能用指令新增提交：

1

git commit -m "標題" -m "內容行 1" -m "內容行 2"

檔案提交完畢後，再用指令完成整個變基：

1

git rebase --continue

推送（push）

變基後推送到遠端伺服器一定會發生衝突，因為本地端與遠端的父節點（parent node）不一致。如果操作的分支有其他人一同作業，推送的模式一定要選擇 Force With Lease，才不會覆蓋掉他人的提交。

結論

通常，變基用於保持一個乾淨、直線的提交歷史，在我目前的專案中會儘量使用變基而不是合併分支。

不過合併可以保留分支間的歷史脈絡，這部分會依團隊內的習慣、權限、策略決定，當需要保持完整的開發歷程紀錄時，合併分支是更合適的選擇。團隊內最終勢必會有一個人負責整理整個儲存庫（或沒有？），讓它儘可能乾淨、整潔又能追溯，而這往往取決於當初提交的那個人有沒有好好寫提交訊息，供後人追蹤與整合。

無論是變基還是合併，都有可能遇到衝突。面對不熟的儲存庫時，掌握度不夠就不知道該怎麼解決合併衝突，建議先把程式碼摸熟一點再動手。要避免麻煩的失誤，操作前建議先開一個新的分支。如果遇到任何問題，使用 git rebase --abort 可以隨時撤銷變基。確定變基成功或是沒有衝突，再將原本的分支刪除，並把暫存分支改名。

在面對像屎般、又臭又長的提交，或許直接全部壓縮也不無是一種好的方法，畢竟某些提交 5 年以上了，又沒有寫提交訊息的情況下，鬼才知道他當初為了什麼而提交。不過討論到最後又是整個公司制度的事情了。
