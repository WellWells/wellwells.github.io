內網 HTTPS 無痛升級：使用 OpenSSL 建立自簽署憑證

用 OpenSSL 產生私鑰、CSR 與自簽署憑證，套到 Nginx、Docker 等內網服務上，再把憑證匯入 Windows、macOS、Linux 的根憑證庫，讓瀏覽器不再跳警告。

前言

在開發或內部測試階段，經常需要部署多種服務，例如：

  1. Nginx 架設網頁伺服器，分發流量或提供靜態資源
  2. AdGuardHome 做 DNS over HTTPS（DoH），阻擋廣告並保護隱私
  3. Node.js 或 Deno 部署動態應用（如 API 或全端框架 Next.js）
  4. Docker 容器服務

內網服務架好之後，如果登入頁面要輸入密碼，瀏覽器在未使用 HTTPS 協定時會提示此連線不安全，本文章將說明如何產生自簽署憑證（self-signed certificate）並應用於該服務，最終於系統中信任該憑證。

什麼是 HTTP(S)

HTTP（HyperText Transfer Protocol）與 HTTPS（HyperText Transfer Protocol Secure）是常用於資料傳輸的應用層協定，負責定義應用程式之間如何交換資料。其中，HTTP 是明文傳輸，容易被駭客或第三方攔截並分析未加密的資料，如帳號密碼或敏感資訊。相較之下，HTTPS 是基於 HTTP 並加入 TLS（Transport Layer Security）加密協定的版本，靠加密做到資料的機密性、完整性與身分驗證，即使資料遭到攔截，也無法被解讀或有效利用，降低敏感資訊外洩的風險。

TLS 是 SSL（Secure Sockets Layer）的後繼版本，從 1999 年起取代 SSL 成為網路加密的標準協定。相比已經廢棄的 SSL，TLS 有更高效的握手流程、改進的加密演算法，以及針對已知漏洞的修正。目前推薦使用 TLS 1.2（2008 年推出）或 TLS 1.3（2018 年推出），通訊安全性才符合現代標準。雖然 SSL 這個術語仍被廣泛使用來泛指加密協定，但現今的 HTTPS 通訊都是基於 TLS。像 OpenSSL 這樣的開源工具庫，是實作 TLS/SSL 協定的重要工具，支援憑證的建立、簽署與驗證等操作，也是建立 HTTPS 安全環境的核心。

什麼是憑證

憑證是 HTTPS 安全性的核心要素之一。HTTPS 用數位憑證驗證伺服器的身分，這個數位憑證通常依照 X.509 規範產生，該規範訂定了伺服器的身分資訊（如域名）、公鑰、有效期限、簽發機構以及其他延伸屬性。受信任的憑證授權機構（certificate authority，CA）對這些資訊做數位簽章，保證憑證的完整性與可信度，防止中間人攻擊與假冒伺服器的行為。

要產生 X.509 憑證，首先要產生一組密鑰對，其中包含：

  • 私鑰（Private Key）：用於加密資料或做數位簽章，且必須妥善保管，不可公開。
  • 公鑰（Public Key）：公鑰用於加密資料，或驗證由私鑰簽章的資料，用來確認資料的完整性與來源的真實性。公鑰是由私鑰透過非對稱加密演算法計算得出，與私鑰配對使用，但無法從公鑰反推出私鑰。

用私鑰產生的公鑰可以建立憑證簽署請求（certificate signing request，CSR），CSR 是產生憑證的基礎檔案。把 CSR 提交給 CA 後，CA 作為信任機構，會根據 CSR 中的資訊驗證伺服器的身分，並使用其中的公鑰簽署並產生正式的憑證，用於伺服器身分驗證和加密通訊。CSR 中包含：

  • 主機名稱（Common Name, CN）：例如域名 wellstsai.com。
  • 組織資訊：包含公司名稱、國家、地區等相關資訊。
  • 公鑰：由私鑰產生，嵌入到 CSR 檔案中，用於身分驗證與加密通訊。

如果是提交給 CA，CA 在完成伺服器身分驗證後，會使用他們自己的私鑰對 CSR 做數位簽章，並設定憑證的有效期限，最終產生正式的 X.509 憑證。

如果是自簽署，就不需要 CA 的參與。此時可以直接用自己的私鑰對 CSR 做數位簽章，產生自簽署的 X.509 憑證。自簽署憑證在技術上功能一樣完整，但不被公共信任機構認可，所以適用於內部測試環境或私有系統。

最終，在伺服器上設定所產生的私鑰與憑證，並將其整合到伺服器的 HTTPS 設定中（如 Nginx）。當使用者在瀏覽網頁時，瀏覽器會自動與伺服器跑一次數位憑證的認證流程。

瀏覽器會判斷憑證是否由受信任的 CA 簽署、是否仍在有效期內，以及是否與存取的域名相符。如果這些條件都符合，瀏覽器會在網址列左上方顯示連線安全的鎖頭圖示，表示該網站的憑證有效且可信。隨後，瀏覽器與伺服器會進一步建立加密通訊通道。在建立通訊通道的過程中，雙方會透過金鑰交換演算法（如 ECDHE）各自算出同一組對稱加密密鑰，伺服器則以憑證公鑰對應的私鑰對交握內容簽章，讓瀏覽器確認對方確實持有該私鑰。後續的資料傳輸就改用這組對稱密鑰加解密（速度較快）。這樣一來，使用者與伺服器之間的通訊內容（如瀏覽資料、提交表單等）都會用對稱加密與解密保護，防止第三方（如中間人或惡意攻擊者）竊取或竄改傳輸中的資料。

#!/bin/bash

# 定義變數
OUTPUT_DIR="$HOME/certificates"
KEY_FILE="$OUTPUT_DIR/wells_server.key" # 私鑰
CSR_FILE="$OUTPUT_DIR/wells_server.csr" # CSR 檔案
CRT_FILE="$OUTPUT_DIR/wells_server.crt" # 憑證
DAYS_VALID=365
COUNTRY="TW"
STATE="Taiwan"
CITY="Taipei"
ORG="WellsTsai"
OU="wells_server"
CN="wells_server"

# 憑證適用的域名或 IP 位址
SAN="DNS:wells_server,DNS:localhost,IP:127.0.0.1,IP:192.168.1.100"

# 建立輸出目錄
mkdir -p "$OUTPUT_DIR" || { echo "無法建立目錄 $OUTPUT_DIR，腳本已終止"; exit 1; }

# 檢查並安裝 openssl
if ! command -v openssl &> /dev/null; then
    echo "openssl 不存在，腳本已終止"
    exit 1
fi

# 建立 ECC 私鑰
echo "建立 ECC 私鑰..."
openssl ecparam -genkey -name prime256v1 -out "$KEY_FILE" || { echo "ECC 私鑰建立失敗，腳本已終止"; exit 1; }

# 建立 CSR 檔案
echo "建立 CSR 檔案..."
openssl req -new -key "$KEY_FILE" -out "$CSR_FILE" \
    -subj "/C=$COUNTRY/ST=$STATE/L=$CITY/O=$ORG/OU=$OU/CN=$CN" \
    -addext "subjectAltName=$SAN" || { echo "CSR 檔案建立失敗，腳本已終止"; exit 1; }

# 建立自簽署憑證
echo "建立自簽署憑證..."

# 建立臨時檔案
SAN_CONF=$(mktemp) || { echo "無法建立臨時檔案，腳本已終止"; exit 1; }
chmod 600 "$SAN_CONF"

# 將 SAN 設定寫入臨時檔案
printf "[v3_req]\nsubjectAltName=$SAN" > "$SAN_CONF"

openssl x509 -req -days "$DAYS_VALID" -in "$CSR_FILE" -signkey "$KEY_FILE" -out "$CRT_FILE" -extfile "$SAN_CONF" -extensions v3_req \
    || { echo "自簽署憑證建立失敗，腳本已終止"; rm -f "$SAN_CONF"; exit 1; }

# 清理臨時檔案
rm -f "$SAN_CONF"

# 顯示完成訊息
echo "憑證已建立！"
echo "私鑰: $KEY_FILE"
echo "CSR 檔案: $CSR_FILE"
echo "憑證: $CRT_FILE"

這邊我的本地端伺服器名 wells_server，如果有實際域名像是 wellstsai.com，則填寫對應的域名、IP 位址。

從腳本中可得知，首先會建立私鑰，並產生 CSR 檔案。CSR 檔案需包含相關的域名、地理資訊。

其中 CSR 中的 subjectAltName（subject alternative name，SAN）是 X.509 憑證的延伸屬性，主要用於指定憑證適用的多個主機名、域名或 IP 位址。SAN 欄位中的這些名稱會被寫入憑證中，瀏覽器或其他使用者端才能正確驗證憑證是否與請求的資源相符。

自 2017-04 起，Chrome 58 版本及其他基於 Chromium 的瀏覽器（如 Chrome 和 Edge）停止用憑證的 CN 欄位驗證主機名稱，而改為僅依賴 SAN 欄位。這使 SAN 成為現代憑證設定中的必要屬性。

最後產出 CSR 檔案後，使用私鑰自簽署該憑證。

執行腳本

確認域名設定正確後，儲存修改，並為腳本新增執行權限：

1

chmod +x ~/generate_tls_cert.sh

接著執行腳本以產生憑證：

1

~/generate_tls_cert.sh

執行腳本後，使用者目錄下的 ~/certificates/ 資料夾內會產生三個檔案，分別對應私鑰、CSR 檔案與憑證。

系統安裝自簽署憑證

使用自簽署憑證設定伺服器時，因未經 CA 認證，系統或瀏覽器不會自動信任該憑證。因此，需手動將憑證加入信任列表，否則系統或瀏覽器會警告連線不安全，並顯示憑證未被信任的提示。

以下以 Windows 為主，說明如何將自簽署憑證匯入系統。

用 scp [使用者]@[伺服器]:[檔案路徑] [本機路徑] 或是 VS Code 把伺服器的檔案抓下來至本地。

1

scp wells@wells_server:~/certificates/wells_server.crt C:\Users\wells

下載完成後，可以用圖形介面或是指令安裝憑證。滑鼠點兩下 wells_server.crt，點選安裝憑證，選擇目前使用者作為存放範圍，並將憑證存放於受信任的根憑證授權單位

或是用終端機指令存放於目前使用者的受信任的根憑證授權單位：

1
2
3
4
5
6
7
8
9

# For Windows, CMD
certutil -user -addstore "Root" C:\Users\wells\wells_server.crt

# For macOS
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ~/wells_server.crt

# For Linux
sudo cp ~/wells_server.crt /usr/local/share/ca-certificates/
sudo update-ca-certificates

關閉瀏覽器，重新開啟後連接至相關服務的網址。此時該左上方瀏覽器中顯示的憑證狀態，應標示為受信任的憑證。

常見的憑證授權機構

最後簡要介紹一些常見的 CA。這些機構負責簽發並驗證憑證，證明網站的身分可信。經過 CA 簽署的憑證會自動被作業系統和瀏覽器信任（前提是該 CA 在系統的受信任根憑證庫裡），使用者瀏覽網站時可直接建立加密連線，不會跳出不安全的警告，也能防範中間人攻擊（MITM）。這通常會用在生產階段或是公開的網域中。

根據 W3Techs 統計資料（2024/12/04），以下是主要 CA 及其市占概況：

  1. Let's Encrypt 擁有 59.1% 的網站使用率，市占率達 62.9%。其最大的特點在於提供免費且自動化的憑證服務，特別受到中小型網站和個人開發者的青睞。
  2. GlobalSign 使用率為 20.3%，市占率達 21.6%，主要服務對象為企業和政府機構，以其高安全性和穩定性著稱。
  3. Sectigo 使用率為 6.1%，市占率達 6.4%，以多樣化的憑證產品和經濟實惠的價格吸引不同規模的企業使用者。
  4. GoDaddy 市占率達 4.3%。該 CA 主打中小企業市場，提供便捷的域名與 SSL 憑證整合服務。
  5. DigiCert 使用率為 4.0%，市占率達 4.2%，專注於高安全性和企業級需求，適用於金融和高風險行業的應用場景。

結論

這篇說明了如何用 OpenSSL 建立自簽署憑證，並套用到內部伺服器與容器服務（如 Nginx 和 Docker）。自簽署憑證不適用於公開網站，但在內部測試或開發階段，它是最省事也最省錢的做法。

內網環境的 IT 人員只要在伺服器上統一部署自簽署憑證，再把它加進內部系統的受信任憑證庫，就能把整個內網的 HTTPS 一次補齊。

憑證的主要目的是建立伺服器與使用者之間的安全連線。雖然自簽署憑證不被公共 CA 認可，但在手動信任正確憑證後，即使遭受中間人攻擊，攻擊者也無法偽造與原憑證相符的私鑰，瀏覽器會因為憑證不符而提示不安全，攻擊也就擋下來了。

先前的文章：《深入解析臺灣 DNS RPZ 網路封鎖與解鎖策略》，也曾提到類似的憑證錯誤問題。該情境中，憑證錯誤是因原網站的憑證被 DNS 脅持所導致，這進一步說明了正確設定憑證與驗證其可信性的重要性。
