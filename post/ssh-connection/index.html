引言

Secure Shell（SSH）是一個安全協定，允許兩台電腦在加密的連線上交換資料（執行命令、傳檔案），保證資料的安全與完整性。

SSH 通常用於兩台電腦的遠端登入。它取代了舊的遠端存取協定，像是 Telnet 是以明文沒有加密的方式傳輸密碼和內容。而 PTT 也在 2022 年關閉不安全的 Telnet 協定，改用 SSH 或是 WebSocket 協定，讓通訊過程都有加密，防止竊聽與竄改。

SSH 除了裝置遠端連線，還可以：

  • 建立 SSH 隧道（Tunneling）做連接埠轉發，安全地存取網路資源。
  • SFTP、SCP 可以安全地上傳或下載檔案。
  • rsync 用於檔案同步，減少傳輸用量。

Linux、macOS 或是 Windows 預設都整合了 OpenSSH 套件。OpenSSH 是一套開源的 SSH 實作，本文會用到的工具有：

  • ssh，遠端登入到其他主機並執行命令。
  • scp，在本地與遠端之間傳輸檔案。
  • ssh-keygen，產生 SSH 金鑰對（公鑰和私鑰）。
  • ssh-add，將私鑰加入 ssh-agent。
  • ssh-agent，在用戶端保存使用者的 SSH 金鑰，並在需要時拿這些金鑰驗證身分。
  • sshd（SSH Daemon），在伺服器上執行的常駐程式，負責接受用戶端的 SSH 連線請求。

本文著重於建立公鑰與私鑰，並用這兩把鑰匙做到免密碼認證，也會說明伺服器端如何執行 SSH 服務，讓用戶端連上來。

傳統的密碼登入方式，是輸入正確的使用者密碼來驗證身分。若伺服器暴露在公共網路上，可能會面臨暴力攻擊的風險，導致伺服器資料外洩。

為了提升安全性(與懶得輸入密碼?)，可以改用公私鑰驗證。如此一來不需要輸入密碼就可以連線，且駭客在沒有私鑰的情況下也無法登入。

💡 本文章有使用 Tailscale 建立內網，讓本地端與伺服器端的電腦可以用 hostname 或是 IP 位址連線。

兩台電腦要連線需要有 IP 位址，如果是公網 IP 位址則需要在路由器設定連接埠轉發到內網，但暴露 SSH 連接埠的風險相對高。 不想暴露連接埠、沒有公網 IP 位址或是無法修改路由器設定等，可閱讀《使用 Tailscale 輕鬆建立安全且私密的隧道》，讓兩台電腦連上線。

SSH 金鑰建立與連線流程

nodeA 是本地端，也就是工作用的電腦。nodeB 是伺服器端，也就是被連線的電腦，例如 git 伺服器、網頁伺服器或虛擬專用伺服器。

  1. 在 nodeA 或 nodeB 產生金鑰（公鑰與私鑰）。
  2. 把私鑰放在 nodeA，公鑰放在 nodeB。公鑰可以公開，私鑰只有自己能存取，nodeB 上不留私鑰。
  3. nodeB 建立 ~/.ssh/authorized_keys，並填入公鑰。
  4. nodeA 建立 ~/.ssh/config，填入連線資訊，連線資訊包含伺服器 IP 位址與私鑰路徑。
  5. nodeA 之後用 config 裡的 Host 名稱連線，就會使用金鑰。

💡要特別注意的是：

  1. nodeB 如果是 Windows 且登入帳號屬於 Administrators 群組，路徑需改為： C:\ProgramData\ssh\administrators_authorized_keys
  2. 如果連線失敗或設定金鑰後仍要求輸入密碼，參考連線除錯方式。

建立金鑰

在用戶端或伺服器端都可以建立金鑰，Windows 與 Linux 的指令都是 ssh-keygen：

1

ssh-keygen -t ed25519 -C "your_email@example.com"
  • -t ed25519 產生一對 Ed25519 金鑰。OpenSSH 9.5（2023 年）起 ssh-keygen 預設產生 Ed25519，它的金鑰短、效能比 RSA 好，目前絕大多數伺服器都支援，是我個人產金鑰的首選。RSA 的相容性最好，連線到不支援 Ed25519 的舊設備時才需要改用 -t rsa -b 4096，表示 RSA 長度為 4096 位元。
  • -C "xxx" 加入備註，內容可自訂，用來辨識金鑰。

產金鑰時會看到 Enter file in which to save the key，預設路徑是個人目錄的 .ssh 資料夾。

接著會詢問 passphrase（金鑰密碼）。我建議設定 passphrase，駭客就算取得私鑰，還要突破這道密碼。留空則使用金鑰時不需要密碼，但私鑰外洩後可以直接被拿來連線。設定後可搭配金鑰密碼搭配 ssh-agent 快取，不用每次輸入。

使用 SSH 金鑰建立兩台電腦連線

下一步是把公鑰加進 nodeB 的 authorized_keys。這一步還是要用密碼登入 nodeB，所以要在關閉密碼認證之前完成。

一行指令安裝公鑰（nodeB 是 Linux）

nodeA 是 Linux 或 macOS 時，用 ssh-copy-id：

1

ssh-copy-id -i ~/.ssh/nodeA_ed25519.pub wells@nodeB

Windows 沒有內建 ssh-copy-id，在 PowerShell 用以下指令完成同一件事：

1

Get-Content ~/.ssh/nodeA_ed25519.pub | ssh wells@nodeB "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

輸入一次 nodeB 的密碼後就完成了。這行指令會在 nodeB 建立 ~/.ssh、把公鑰附加到 authorized_keys，並設定權限。chmod 不能省略：sshd 預設會檢查權限，其他人可寫入時會忽略金鑰，改回密碼登入。

重複執行這行會在 authorized_keys 多出一行相同的公鑰，不影響登入；ssh-copy-id 則會略過已存在的公鑰。

安裝完成後，接著設定 config。

手動安裝公鑰（nodeB 是 Windows）

Windows 的 sshd 預設使用 cmd.exe，上面的 mkdir -p、chmod 無法執行，需要手動安裝。想自己操作每一步的 Linux 使用者也適用。

先在 nodeB 建立個人目錄底下的 .ssh 資料夾，否則 scp 會因為路徑不存在而失敗。接著用 scp 把公鑰（nodeA_ed25519.pub）複製到伺服器。

用法為：scp 本地檔案路徑 使用者名稱@伺服器:伺服器路徑

Windows 複製公鑰到 Windows

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:C:\Users\wells_nodeB\.ssh\nodeA_ed25519.pub

Windows 複製到 Linux

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:~/.ssh/nodeA_ed25519.pub

輸入密碼後，scp 就會把公鑰複製到伺服器上。

複製後，在 nodeB 上（伺服器端），新增檔案並填入公鑰內容。

路徑依 nodeB 的登入帳號而定

  • Windows 一般使用者：C:\Users\wells_nodeB\.ssh\authorized_keys
  • ⚠️ Windows Administrators 群組成員：C:\ProgramData\ssh\administrators_authorized_keys
  • Linux 一般使用者/root：~/.ssh/authorized_keys
  1. 記事本開啟公鑰 (nodeA_ed25519.pub)
  2. 全選複製內容
  3. 新增上述檔案
  4. 在上述檔案內，貼上公鑰內容後存檔

接著設定 nodeB 上的權限。Linux：

1
2

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Windows 的 administrators_authorized_keys 只能讓 Administrators 和 SYSTEM 存取，用系統管理員權限開啟 PowerShell 後執行：

1

icacls.exe "$env:ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"

設定 config 並連線

本地端 nodeA 新增 config 設定檔後儲存：

  • Windows：C:\Users\wells_nodeA\.ssh\config
  • Linux：~/.ssh/config
1
2
3
4
5

Host nodeB_wells
    User wells
    HostName nodeB
    IdentityFile ~/.ssh/nodeA_ed25519
    IdentitiesOnly yes

設定檔內容說明

  • Host 為個人可辨識的名稱
  • User 是伺服器上的使用者名稱
  • HostName 為伺服器的 IP 位址或 host 名稱
  • IdentityFile 為私鑰路徑，Windows 與 Linux 上都可以使用 ~/ 表示個人目錄
  • IdentitiesOnly 表示只使用 IdentityFile 指定的金鑰，避免 ssh-agent 裡的其他金鑰先被嘗試，累積失敗次數後出現 Too many authentication failures

儲存後，用 config 裡的 Host 名稱連線，此時不會要求輸入密碼

1

連線時要用 nodeB_wells。ssh wells@nodeB 不符合 Host nodeB_wells，不會套用這個區塊的設定，也就不會使用 nodeA_ed25519。

連線除錯方式

如果遠端連線失敗，可在連線時加入 -vvv 排錯，例如：

1
2
3
4
5
6
7

C:\Users\wells_nodeA>ssh -vvv wells@nodeB

OpenSSH_for_Windows_8.6p1, LibreSSL 3.4.3
...
debug1: Connecting to server [100.100.120.16] port 22.
debug1: connect to address 100.100.120.16 port 22: Connection timed out
ssh: connect to host server port 22: Connection timed out

Connection timed out 表示封包沒有收到回應，可能的原因有：

  • 伺服器端的防火牆阻擋連線（電腦、防毒軟體、路由器）。
  • 用戶端的 port 22 被阻擋。
  • IP 位址錯誤或伺服器沒有開機。

其他常見的錯誤訊息：

  • Connection refused：伺服器有回應，但 22 連接埠沒有服務，通常是 sshd 沒有啟動。
  • Could not resolve hostname：DNS 解析失敗，先檢查 hostname 是否正確。

若登入失敗或仍要求輸入密碼，可以檢查：

  • 金鑰是否正確
  • authorized_keys 路徑是否正確
  • Linux 的 ~/.ssh 權限是否為 700、authorized_keys 是否為 600，個人目錄是否只有自己能寫入
  • Windows 的 administrators_authorized_keys 是否已設定權限
  • 連線時是否使用 config 的 Host 名稱

進階安全設定

關閉密碼認證

確定金鑰可以成功登入後，可以關閉 nodeB 的密碼認證提高安全性。

設定檔路徑：

  • Windows：C:\ProgramData\ssh\sshd_config
  • Linux：/etc/ssh/sshd_config

找到約 50 行附近，並將 PasswordAuthentication 改為 no，記得移除前面的 #

1
2

-#PasswordAuthentication yes
+PasswordAuthentication no

修改後重新啟動 sshd，下次登入僅使用金鑰進行，若金鑰遺失則無法登入。重新啟動前先確認金鑰可以登入，並保留一條已登入的連線，設定有誤時才能改回來。

用 PowerShell 重新啟動 sshd

1

Restart-Service sshd

Linux 重新啟動 sshd

1

sudo service ssh restart

Ubuntu 要再確認實際生效的值。sshd 採用第一個讀到的設定，而 sshd_config 開頭會先載入 /etc/ssh/sshd_config.d/ 底下的檔案。如果 50-cloud-init.conf 含有 PasswordAuthentication yes，上面的修改就不會生效，要一起修改該檔案。

1
2
3
4
5

# 顯示 sshd 實際使用的值
sudo sshd -T | grep -i passwordauthentication

# 找出覆蓋設定的檔案
sudo grep -r PasswordAuthentication /etc/ssh/sshd_config.d/

金鑰密碼搭配 ssh-agent

ssh-agent 會保存解密後的私鑰，只要輸入一次 passphrase，之後都由 ssh-agent 驗證金鑰。

Windows 底下的 SSH 執行檔分為兩包：

  1. OpenSSH 底下的 C:\Windows\System32\OpenSSH
  2. Git 目錄底下的 C:\Program Files\Git\usr\bin

所以 Windows 要把 Git 的 sshCommand 改為 OpenSSH 的路徑。

git config --global core.sshCommand C:/Windows/System32/OpenSSH/ssh.exe

ssh-add C:\Users\wells\.ssh\nodeA_ed25519

macOS 指令可能有些不同，請參閱解法

Windows 的 ssh-agent 是系統服務，會把私鑰用目前的 Windows 帳號加密後存進 Registry，重新開機後依然可用，不用再輸入 passphrase。確定 ssh-agent 已載入私鑰後，微軟建議把私鑰備份至安全的地方，並從此電腦上移除。

只要 ssh-agent 有成功啟動，預設都會由 agent 做金鑰認證。

最終，Windows 上 nodeA 的 .ssh 資料夾應該只有 known_hosts 與 config。

config 裡面的 IdentityFile 和 IdentitiesOnly 也要一起移除，只留 IdentitiesOnly 時，ssh 不會使用 agent 裡的金鑰。

1
2
3

Host nodeB_wells
    User wells
    HostName nodeB

Linux 的 ssh-agent 只把私鑰放在記憶體，重新開機後要再執行一次 ssh-add，所以私鑰檔案和 IdentityFile 都要保留。

ssh-agent 預設時間是永久。Linux 若要提高安全性，可以在加入私鑰時設定快取時間：

1

ssh-add -t 1h ~/.ssh/nodeA_ed25519

Windows 的 ssh-agent 不支援快取時間，加上 -t 會被拒絕，不再使用時要用 ssh-add -D 刪除。

使用 SSH agent 轉發

若要在 nodeB 上 git clone GitHub 的程式碼，私鑰不需要放到 nodeB，可以用 SSH agent 轉發。前提是 GitHub 與 nodeB 都已填入公鑰，nodeA 也已經用 ssh-add 把私鑰加進 ssh-agent。

1
2

# 加入 -A 可以啟用 SSH 代理轉發。允許在遠端伺服器上使用本地的 SSH 金鑰。
ssh -A nodeB_wells

也可以在 config 內新增 ForwardAgent，不用每次加 -A：

1
2
3
4

Host nodeB_wells
    User wells
    HostName nodeB
    ForwardAgent yes

連線後，在 nodeB 用 ssh-add -l 檢查轉發過來的金鑰，私鑰本身不會複製到 nodeB。若有列出金鑰，就可以在 nodeB 上 git clone。

我在 2023 年用 Windows 內建的 OpenSSH 8.6p1 做 agent 轉發時，git clone 出現公鑰認證失敗，手動安裝 8.9p1 後才恢復正常。

如果 nodeB 的信任度不高（例如上面有其他使用者擁有 root 權限），不建議使用 agent 轉發：連線期間，nodeB 的 root 可以透過轉發過來的 agent 認證其他主機。

只是要經由 nodeB 連到第三台主機時，可以改用 ProxyJump 把 nodeB 當跳板。私鑰留在 nodeA，nodeA 直接和目標主機認證，nodeB 只轉送加密流量。

1

ssh -J nodeB_wells wells@nodeC

ProxyJump 無法讓 nodeB 上的程式使用金鑰。如果一定要在 nodeB 上存取 GitHub，可以改用只綁定單一 repo 的部署金鑰（deploy key）。

使用 SSH 金鑰存取位於 Synology 上的 Git 伺服器

將公鑰放到 Synology 個人使用者目錄的 .ssh 資料夾，沒有目錄就自行建立，再新增 authorized_keys 並填入公鑰內容。

在本地端的 config 加入 NAS 的設定，User 為 NAS 登入帳號，HostName 為 NAS IP 位址：

1
2
3
4

Host NAS
    User wells
    HostName 192.168.50.12
    IdentityFile ~/.ssh/nodeA_ed25519

git remote 的網址要使用 Host 名稱（例如 NAS:/volume1/git/project.git），才會套用這段設定並使用金鑰認證，不用輸入密碼。

如果設定後仍要求輸入密碼，先確認 DSM 已啟用使用者家目錄服務，再檢查權限。sshd 不接受群組或其他人可寫入的個人目錄，用密碼 SSH 登入 NAS 後修正：

1
2
3

chmod 755 ~
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
