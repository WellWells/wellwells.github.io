前言

在啟動新專案時，許多開發者都會卡在同一個地方，也就是技術選型的決策癱瘓。

已經構思好專案需求與核心功能，開啟開發環境準備實作，卻發現自己必須先回答一連串技術問題：該選用哪個框架？資料庫要用哪套？前後端要如何整合？

於是開始在 Stack Overflow、GitHub Discussions、Reddit 等技術社群中搜尋答案。A 框架的支持者強調其生態系完整、開發效率高；反對者則指出其打包體積龐大、效能堪憂。B 方案的官方文件看似完善，實際採用後卻發現社群支援薄弱、範例程式碼過時。

數小時後，瀏覽器累積了數十個技術文件分頁，筆記中記錄了各種框架的優缺點比較，但實際業務邏輯的程式碼仍是零行。

這正是傳統開發流程的核心問題。在資訊過載的環境下，技術決策的成本被拉高，真正的開發工作卻遲遲無法啟動。

以下列舉三個我親身經歷的技術選型案例。這些決策在當下看似合理，實際執行後才發現方向錯誤，而問題的根源往往是過度依賴搜尋引擎的片面資訊，缺乏對長期技術挑戰的整體評估。

GUI 圖形介面開發的抉擇

以桌面應用程式開發為例，光是選擇圖形使用者介面（graphical user interface，GUI）框架就是一道難題：

這次該採用 C# WPF 還是 Python GUI？還是走前後端框架 Electron、Tauri？

如果專案有跨平臺需求（需要同時支援 Windows、macOS 與 Linux），選擇就更加複雜。以下簡介各項主流技術：

技術方案簡介跨平臺支援適用情境
C# WPF/WinForms微軟推出的 .NET 桌面開發框架，整合度高、生態系成熟❌ 僅限 Windows專為 Windows 平臺量身打造的企業應用
Python GUI（Tkinter/PyQt）Python 生態系的 GUI 解決方案，開發門檻低✅ 支援快速原型開發、資料分析工具、輕量級應用
Electron基於 Chromium 與 Node.js，使用 HTML/CSS/JavaScript 開發桌面應用✅ 支援需要豐富 Web 技術與 npm 生態系的應用，如 VS Code、Slack
Tauri以 Rust 為核心的輕量級替代方案，打包體積小、效能佳✅ 支援追求極致效能與小型安裝檔的現代應用

每種方案各有優劣。Electron 生態系成熟但打包後體積龐大（250 MB~500 MB）；Tauri 輕量高效，但需要 Rust 環境；C# WPF 功能完整，卻無法跨平臺；Python GUI 開發快速，但介面質感通常較為陽春。

資料庫選型的陷阱：全文檢索需求

另一個常見痛點是資料庫選擇，尤其當專案需要 全文檢索（full-text search，FTS） 功能時：

資料庫要選 MongoDB、Elasticsearch，還是 PostgreSQL？

面對未知領域，我們通常的第一步就是上網搜尋。看到有人說 NoSQL 好用，理由是「不用寫 SQL 語法、Schema 彈性高」，便一頭栽進去選用了 MongoDB。

但當專案需要支援中文搜尋時，問題就來了。MongoDB 原生的中文斷詞支援可以說是幾乎沒有。 它的全文索引是基於英文空格分隔設計的，對中文這類無空格分隔的語言束手無策。

什麼是斷詞（tokenization）？ 全文檢索的核心在於「斷詞」。以「臺北市政府」為例，斷詞器會將其拆解為「臺北」、「市」、「政府」等詞彙單元，才能建立有效的索引供搜尋使用。英文單字之間有空格自然分隔，但中文、日文等語言的文字是連續的，必須依賴斷詞器進行切分。

當你在網路上搜尋解決方案時，通常會被引導至兩條路：

  1. 第一條路是採用 MongoDB 官方的付費雲端服務 Atlas Search，這不用多做解釋，反正就是付費了事。
  2. 另一條路則是自建 MEK Stack（MongoDB + Elasticsearch + Kafka）。你需要使用 Docker 分別建立三個獨立服務。資料存入 MongoDB 後，用 Kafka 把資料同步至 Elasticsearch，最終由 Elasticsearch 負責搜尋功能。雖然架構看起來很專業，但對於個人開發者而言，維護成本極高且過於複雜。很可能你的專案還沒正式運作，光是搞定這套分散式系統的維運就先被搞死了。

相較之下，PostgreSQL 才是對個人開發者而言最高效且最快的解法。

它內建全文檢索功能，搭配 zhparser 即可支援中文斷詞，讓你無需額外維護任何服務，就能在單一資料庫內同時滿足資料儲存與搜尋需求。

JavaScript 執行環境的抉擇

除了資料庫選型，JavaScript 執行環境的選擇也是一道難題。

市面上主流的選項包括 Node.js、Deno 與 Bun。

Deno 確實有幾個特性值得一看：

  • 安全沙箱機制：預設採用權限管控，需明確授權才能存取檔案系統、網路或環境變數，執行時的安全性比較有保障。
  • npm 相容性（npm Compatibility）：自 Deno 1.28 起支援直接引用 npm 套件，不再受限於專屬模組系統。
  • 零設定理念：內建 TypeScript、Linter、Formatter、Testing 等工具，無需繁瑣的環境設定即可立即開發。

這些特色對想要現代開發體驗的工程師來說確實有吸引力。

但實際應用時，Deno 與現有成熟生態系整合仍困難重重：

  • 無法與 Electron 整合：Electron 深度綁定 Node.js 架構，要將其替換為 Deno 幾乎不可行，開發體驗欠佳。
  • 主流框架支援不足：Next.js 等廣泛採用的框架與 Deno 的整合仍有諸多問題待解，而 Deno 官方推薦的 Fresh 框架，雖屬原生最佳化方案，但社群規模與生態系資源遠不及 Next.js 成熟。
  • 社群支援薄弱：缺乏活躍社群與夠用的第三方套件支援，開發者在實務上很難快速做出成熟穩定的應用程式。

去年年底我曾嘗試使用 Deno 進行開發，滿懷期待地投入，最終卻發現遇到一堆相容性問題，而這些問題在 Node.js 環境下根本不會發生。例如 Electron 搭配 Deno 的組合，用起來就是很糟；想改用 Tauri 來替代，結果又得先折騰 Rust 開發環境的建置。

這些坑都不是 Deno 本身的問題，是社群還沒長到那個規模。

雖然 Node.js 早期並不原生支援 TypeScript（近期版本已開始逐步整合），但這從來不是問題。因為主流建置工具如 Vite、Webpack 早已將 TypeScript 編譯流程整合得相當完善，開發者幾乎無感。相較之下，Node.js 加上成熟的工具鏈生態系，在穩定性與相容性上仍遠勝於這些新興替代方案。

所以工具選對很重要。

然而在正式動手撰寫核心業務邏輯之前，往往已經把大量時間耗費在瀏覽網頁、閱讀軟體開發套件文件、研究各種框架的規範與樣板專案上。精力被這些繁瑣的設定與學習成本消耗殆盡，這就是大多數開發者的真實日常。

Agentic Workflow：先規劃，再實作

從技術選型焦慮到策略性對話

前文提及的種種困境（GUI 框架的抉擇、資料庫選型的陷阱、執行環境的相容性難題）其實都指向同一件事，在資訊不足的情況下就過早陷入技術細節的泥沼。

傳統開發模式的典型路徑是：看到需求 → 上網查資料 → 被各種框架、工具的行銷話術吸引 → 憑直覺做出選擇 → 開始寫程式 → 發現問題 → 推翻重來。這種「邊做邊學、邊踩雷邊調整」的模式，不僅耗時耗力，更可能因為技術選型錯誤，導致專案在後期難以挽回。

Agentic Workflow 的核心，正是要打破這個惡性循環。

現今，無論是 Antigravity 還是 GitHub Copilot，新一代的 AI 開發工具皆導入 AI Agent（智慧代理）與 Planning（規劃）的核心概念。這代表了一種開發思維與方法論的根本轉變。

新工作流程：溝通、確認、討論

在這套新的工作流程中，不會一開始就急著動手寫程式碼，而是先跟 AI Agent 深度對話：

  1. 溝通：清楚描述你的願景與具體需求。
  2. 確認：讓 Agent 複述並確認其正確理解了你的目標。
  3. 討論：針對系統架構與實作細節進行深入探討，提前辨識潛在風險與問題。

跑完溝通、確認、討論這三步，才真正進入實作階段。這種先規劃再執行的策略，能避免寫了又改、改了又刪的低效迴圈。

實戰案例：從構想到實現

以下透過三個近期實作的專案，展示 Agentic Workflow 如何在真實場景中發揮作用。

專案實踐 1：無限臺灣

展示頁面：無限臺灣

這是一款以珍珠奶茶、台積電、夜市等在地元素為核心的無限合成遊戲。

最初的構想是打造專屬臺灣版本的 Doodle God 或 Infinite Craft。只要具備前後端開發的基礎知識，就能快速實作出可運作的原型。

我以 Vite + React 作為標準技術組合，從官方提供的專案樣板出發，搭配 Tailwind CSS v4 與 TypeScript 快速建立初步架構。在逐步迭代的過程中，透過與 Agent 的持續溝通，隨時針對各項細節進行最佳化。

為了讓執行效能再好一點，最終將專案遷移至 Preact（輕量化的 React 替代方案），並導入 VitePWA 做漸進式網頁應用程式（progressive web app，PWA）快取。針對圖片載入體驗問題，經與 Agent 討論後採用了低品質圖片占位符（low quality image placeholder，LQIP）技術。這讓整個專案的開發節奏變得相當明快。

反倒是圖片與音樂素材的產出最為耗時。這部分主要透過 Gemini 或 ChatGPT 進行內容調整與最佳化，並運用 Suno 等 AI 音樂工具來輔助創作。

在圖片處理方面，雖然嘗試過使用 Illustrator 做向量轉換，但匯出的 SVG 檔案往往過於龐大複雜。所以最後還是採用 WebP 格式做靜態資源編譯與最佳化，兼顧畫質與載入效能。

目前正針對遊戲機制與玩法進行持續改進，未來可能會再加入多國語系支援這類較為繁瑣的功能擴充。

專案實踐 2：臺灣 DNS 查詢器

展示頁面：DNS 封鎖查詢

在先前的文章《深入解析臺灣 DNS RPZ 網路封鎖與解鎖策略》中，我探討了臺灣回應策略區域的相關議題。雖然平時我使用自架的 DNS 伺服器進行解析，因此不受封鎖影響，但突然有個構想：如果要製作一個公開的查詢工具，該如何實作？

由於涉及 DNS 查詢功能，勢必需要後端服務支援。我對 Cloudflare Workers 較為熟悉，決定採用這項無伺服器運算（serverless computing）服務來實作查詢邏輯。但我也希望能記錄查詢歷史並做統計分析，這就需要資料庫支援。我不確定是否需要大費周章自行架設 PostgreSQL，還是有更適合 serverless 架構的輕量方案。

我要開發一個超輕量的網頁前端，主要目的是實作「臺灣 DNS 封鎖查詢工具」。

核心功能需求：
1. 使用者輸入網域名稱，前端將請求發送至 Cloudflare Workers 後端。
2. Worker 執行 DNS Query（針對 101.101.101.101:53 進行查詢）。
3. 判斷邏輯：若解析結果為 150.242.101.120，表示該網域已被 DNS 劫持；反之則為正常。
4. 資料紀錄：無論查詢結果為何，皆須於後端留下紀錄。

預期達成目標：
- 建立查詢統計資料。
- 前端呈現「熱門查詢」與「熱門已封鎖網域」排行。
- 提供設定教學，引導使用者將 DNS 更換為 1.1.1.1 或 8.8.8.8。

技術疑慮：
我不確定後端資料紀錄的最佳實務做法。是否仍需自行架設 PostgreSQL？這樣維運成本是否過高？有沒有更輕量、更適合 serverless 架構的替代方案？

Agent 分析後指出，對於這類輕量級應用，自行架設 PostgreSQL 並非必要。建議採用 Cloudflare D1（基於 SQLite 的分散式資料庫服務）作為替代方案，這能與 Workers 深度整合，形成完整的 serverless 技術堆疊。

這讓專案有了：

  • 零維運成本：由 Cloudflare 全託管，省去架設與維護資料庫的煩惱。
  • 原生整合：與 Workers 深度整合，開發體驗流暢，效能也夠。
  • 免費額度高：每日 500 萬列讀取、10 萬列寫入，對個人專案很夠用。

Planning 階段的價值就在這裡，先確定方向，再動手實作。若沒有這一步，我可能還在折騰 PostgreSQL 的環境建置；有了 Agent 指引，幾分鐘內就定案了最高效的方案。

實作過程中雖有小坑（如時區顯示錯誤、封鎖 IP 判斷邏輯擴充），但透過快速對話都能迅速解決。

對我而言，這個專案最大的收穫是能在有限的時間內，快速了解並開始使用 Cloudflare D1 與 KV 這些新工具。這讓我在往後的專案中，多了一份可以被評估與考慮的技術選項。

另外，頁面中也提供了 DNS 設定教學。回顧整個開發過程，我覺得架設這類頁面最大的困難點還是在於圖片的處理，而非前端排版本身。

專案實踐 3：GemTube

這是一款旨在最佳化 Gemini 使用體驗的瀏覽器擴充功能：GemTube。

原先我的開發習慣多是撰寫使用者腳本（userscripts）來實作各種小工具，但分享時卻發現這對終端使用者極不友善，他們必須先安裝 Tampermonkey，甚至要搞懂怎麼安裝自訂 JS 檔案，步驟相當瑣碎。

透過 Planning + Agent，可以迅速將分散的數個腳本合而為一，轉化為專注於改善 Gemini 與 YouTube 互動體驗的正式擴充功能。

在 GemTube 開發過程中，針對幾個明顯的痛點進行了最佳化：

  1. 缺乏便捷的搜尋引擎整合：

    先前我在《用 ChatGPT 搜尋取代 Google 並預設開啟臨時聊天的方法》一文中，介紹了如何透過 URL 參數將 ChatGPT 新增為瀏覽器搜尋引擎，並預設開啟暫存對話模式。

    但 Gemini 目前沒有類似的 URL 參數機制，也無法用 URL 直接指定要用哪個模型。我希望能將同樣便捷的使用體驗移植到 Gemini 平臺上。

  2. 影片摘要流程過於繁瑣：

    在另一篇《透過 ChatGPT 進行 YouTube 影片分析與總結》文章中，我分享了運用腳本快速擷取影片逐字稿的方法。

    雖然該方案解決了逐字稿抓取的問題，但仍需手動將文字內容複製貼上至 GPT 進行分析處理。

    好在 Gemini 後端已經直接跟 YouTube 整合，貼上影片網址就能分析內容，中間不用再做文字轉換或複製逐字稿。 但我仍希望能把複製網址到開啟 Gemini 分析這段操作流程自動化。

  3. URL 參數支援度不足：

    Gemini 原生並不支援透過 URL 參數（例如 ?q=...）來自動填入對話框並送出查詢，更遑論自動切換模型了。

為解決上述痛點，我整合了多個獨立腳本，開發出 GemTube。這款工具把流程自動化，也做了完整的設定頁面讓使用者自訂操作行為。

以下是 GemTube 的核心功能與設定細節：

  1. Gemini URL 參數自動化 這是本工具最核心的特色，讓 Gemini 有了原本欠缺的 URL 操控能力。使用者用特定參數就能做到以下操作：

    功能說明URL 參數範例
    僅自動填入文字（草稿模式）?q=Hello+World
    自動填入並立即發送?q=Hello+World&send=true
    切換至特定模型並填入文字?q=Analyze+this&model=2 (例如：Gemini Advanced)
    使用暫存對話 + 模型 2 + 自動發送?q=Code+review&model=2&temporary-chat=true&send=true
    僅啟用暫存對話（不填入文字）?temporary-chat=true

  2. YouTube 影片分析增強 針對 YouTube 觀影體驗，擴充功能提供了深度整合的分析功能：

    • ✨ 快速分析按鈕：在影片下方顯示按鈕，點選後自動擷取資訊並傳送至 Gemini 解析。
    • 自訂分析提示詞：使用者可預設「詳細統整說明分析探討整個影片內容」等指令，讓每次分析都符合預期。
    • 📋 字幕與留言快速複製：啟用後，在不選取文字的情況下按 Ctrl+C，即可自動抓取影片字幕或留言內容，並附加預設的提示詞（如：要求使用臺灣繁體中文、詳細消化轉錄稿資訊）。

Agent 協助實作流程

由於我先前並無開發 Chrome 擴充功能的經驗，過去僅接觸過簡單的使用者腳本，所以我直接把已經寫好的腳本交給 Agent，請它協助做專案初始化與架構轉換。

結論

AI Agent 搭配 Planning 的工作流程，確實是未來軟體開發的核心方向。先規劃後實作，技術門檻低了不少，專案從構想到落地不會再卡在難以跨越的技術鴻溝；更重要的是，專案在初期就往正確的架構走，不會做到一半才發現方向從頭就錯了。

而在實務執行中，切勿過度依賴單一模型。不同模型各有所長，有時 A 模型解不開的邏輯瓶頸，換個模型嘗試往往就能迎刃而解。
