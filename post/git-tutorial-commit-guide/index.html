用 GPT 分析程式碼差異，產生符合規範的 Git Commit 訊息：提交類型、範圍與訊息格式怎麼定，以及在 VS Code 裡怎麼把 diff 丟給 GPT。

前言

軟體開發用 Git 追蹤與管理程式碼的變更，每次提交（commit）都記錄了修改差異、提交描述以及內文。清晰具體的提交訊息能讓團隊成員快速理解變更的原因和實際的改動，程式碼管理和團隊合作也會順暢很多。

實際開發中，一個小功能在正式釋出到主要分支前，常常會微調很多次。變更很細微的時候，就容易忽略提交訊息，標題寫得過於簡略，甚至不寫。隨著提交數量增加，追蹤每次修改的具體內容變得越來越困難，也會影響後續的維護和除錯。

所以修改多個檔案時，建議把變更拆得更細，讓每次提交都對應到具體的改動。這時候用 GPT 這類語言工具可以快速分析變更內容，產生一致且詳細的提交訊息，每次提交都留下清楚的紀錄。

撰寫提交訊息並沒有唯一正確的方式。不同公司有不同的偏好和標準，開發者本身也有自己的習慣。規範化的提交訊息就是讓不同開發者在溝通時，能有更多的一致性與可讀性。

規範化提交內容

規範化提交內容可以儘量統一大家的格式，讓提交訊息更好讀。不考慮特定公司的規則，業界大多數約定成俗的提交訊息格式通常包含以下幾個要點：

1
2
3
4
5

<類別>[範圍(可選)]: <描述>

[內文(可選)]

[備註(可選)]

上述規範並非絕對，但一個好的提交內容至少會用類別、描述以及內文把整件事講清楚。

類型（Type）

提交訊息的類型是最重要的部分，用來描述這次提交的變更類型。常見的類型包括：

類型說明
feat新增功能（feature）
fix修復臭蟲（bug）
docs修改文件（documentation）
style不影響程式碼邏輯的修改（如空白、格式、缺少的分號等）
refactor重構程式碼，既不是新增功能，也不是修復 bug
test新增或修改測試
chore變更建置程式或輔助工具的內容，不影響程式碼邏輯
perf提升效能的修改
ci與持續整合相關的修改
build影響建置系統或外部依賴的變更

當然也不局限於上述類型，也可以像是棄用（deprecate）、釋出（release）等類型，甚至我自己在管理 Hugo 文章的提交，也創造了 post 類型表示一篇新文章的發布。

範圍（Scope）

類型後可以加上範圍，用來指定變更的範圍或模組。這部分是可選的，用來提供更細緻的變更內容，例如：

  • feat(ui)：新增與 UI 相關的功能

  • fix(api)：修復 API 相關的 bug

描述（Description / Subject）

描述部分緊接在類型和範圍後面，用於簡潔地總結這次提交的具體變更。根據慣例，描述使用祈使句(命令)並且保持在 50 字以內，說明程式碼更動的簡短摘要。有助於其他開發者快速理解提交的目的與內容。

⚠️ 描述結尾不句號。

範例：

feat(auth)：新增 OAuth2 驗證機制

fix(database)：修正資料庫連線超時問題

內文（Body）

內文部分需空一行開始撰寫，應以清晰且詳盡的方式解釋此次提交的細節和背景。可以包括：

  1. 變更的原因
  2. 解決了什麼問題或增加了什麼功能
  3. 任何相關的技術細節或考量
  4. 潛在影響（如與其他模組的相容性）

內文可以用 Markdown 排版，例如條列清單、程式碼片段等，以幫助閱讀。每行文字最好保持在 72 個字元以內，在電子郵件或其他工具中才好讀。

別人怎麼寫？

說了那麼多，直接來看看別人怎麼寫😉。

參考以下的範例中，可以歸納出一些共同的規則：

  1. 簡明的標題，通常 50 字以內，使用現在式動詞，不用標點。
  2. 內文根據需要詳細說明改動，引用相關的 issue 編號或審查系統。
  3. 格式標準化（如某些專案使用類別標籤）。
  4. 類別標籤的差異性。有像是中括號表示類別、冒號分隔功能模組與描述、斜線分割模組與子系統標識，會依據團隊或個人的習慣微調。
  5. 加上簽名以標示責任人，特別是在開源專案中。

當然，假設你更動並提交很多檔案，只寫一句 fix login.py，會讓後面接手的人很痛苦，也難以追蹤，還是要好好說明原因，這部分就看你想當一個怎麼樣的開發者。

types/lazy: add DeferredInit type

It is sometimes necessary to defer initialization steps until the first actual usage
or until certain prerequisites have been met. For example, policy setting and
policy source registration should not occur during package initialization.
Instead, they should be deferred until the syspolicy package is actually used.
Additionally, any errors should be properly handled and reported, rather than
causing a panic within the package's init function.

In this PR, we add DeferredInit, to facilitate the registration and invocation
of deferred initialization functions.

⭐ 使用 GPT 快速產生提交內容

熟悉規範化的提交訊息之後，就能套用到實際開發，用 GPT 自動產生提交訊息。以下說明怎麼用 Git 和 VS Code 自動化這個過程。

首先，在 VS Code 把檔案暫存變更（git add）。

之後開啟下方終端機，輸入以下指令產生暫存檔案的 diff log，再用管道（pipe）把結果直接輸出到 VS Code 編輯器。

1

git diff --cached | code -

也可以加入一些 prompt，可以更快地複製 prompt + diff，並貼到 GPT 中。

Windows 底下加上 prompt:

1

cmd /c "chcp 65001 & (echo 參考先前輸出: & git log -n 5 --name-only & echo. & echo 不要撰寫廢話，本次 diff 內容如下，幫我產生出符合 git 規範的提交內容: & git diff --cached) | code -"

Linux 底下加上 prompt:

1
2
3
4
5

# 單純 prompt
{ echo "不要撰寫廢話，本次 diff 內容如下，幫我產生出符合 git 規範的提交內容: "; git diff --cached; } | code -

# 參考先前輸出
{ echo "參考先前輸出:"; git log -n 5 --name-only; echo ""; echo "不要撰寫廢話，本次 diff 內容如下，幫我產生出符合 git 規範的提交內容: "; git diff --cached; } | code -

此時 VS Code 會自動彈出新的視窗，內含 prompt 和暫存區的 diff 內容。把這些內容複製貼到 GPT，就能產生規範化的提交訊息。

不要使用 gitmoji

過去我曾經使用 Gitmoji，這些看起來精美的 emoji 的確為乏味的提交訊息增添了一些趣味。

不過我在把提交轉換成 patch 時，產生 patch 檔案後做內部 apply 遇到了錯誤。具體原因已經不太記得，但應該是提交訊息開頭的符號（例如冒號）導致舊版 Git 在 apply 時失敗。Gitmoji 就是有這種相容性問題，不太推薦使用。

Gitmoji 的使用也缺乏一致的規範。你對圖示的理解可能和我不一樣，這就容易引發誤解。例如：

  1. 🐛 通常用於表示修正錯誤，而 🚑️ 則表示修正緊急錯誤，但它們的界限並不明確。
  2. 🔥 表示移除程式碼。如果因為 🐛（錯誤）而導致程式碼編譯失敗，並且移除了這段程式碼可以解決問題，此時應該使用 🔥 還是 🐛？
  3. 🔒️ 表示修正安全性問題。如果這個安全性問題本質上是因為 🐛（錯誤）導致的，我應該選擇哪個？

這些都是使用 Gitmoji 時容易出現的疑慮，還有更多使用上的困惑就不一一列舉了。

清楚寫出提交訊息的內文，遠比一個別人不見得看得懂的 emoji 更能傳達意圖。

規範提交訊息的類別和範圍，也能更清楚表達這次提交針對的部分和改動的性質。

結論

規範且清晰的提交訊息，對程式碼的可追溯性和後續維護幫助很大，別人也能很快看懂變更內容。用 GPT 這類工具產生，可以省下不少寫訊息的時間，格式也比較一致。

本文舉例的公開專案提交訊息，風格差異不小，但共同的規則沒變：具體的類別、清晰簡明的標題，以及必要時附上的詳細內文與追蹤編號。至於 Gitmoji，考慮到相容性問題和大家對圖示的解讀落差，我自己是不用了。
