前言

在前篇文章控制器區域網路（CAN bus）特性與重點，講述了 CAN 的基本特性、CAN 的種類、差異及資料幀的內容。

傳統的資料傳遞，通常是先定義好特定的 ID，再約定 8 個位元組分別代表什麼訊號，並搭配 DBC 檔案記錄解碼方式。

CAN 協定本身只定義了如何在網路上傳遞資料，並沒有詳細規定資料的內容和格式。因此，需要引入一些進階協定（higher level protocol，HLP），例如 CCP/XCP、CANopen、AUTOSAR、J1939 等，以滿足不同的需求和應用場景。

以未使用 HLP 的 CAN 為例子，我們可能定義 ID 為 0x100 的前 4 個位元組表示車速，範圍為 0 至 150，單位是 km/h；後 4 個位元組表示檔位資訊，其中 1000 表示 P 檔，0100 表示 D 檔，依此類推。不同廠商會有各自不同的定義，通常會使用一張大型的 Excel 表格或 DBC 檔案來記錄並說明解碼方式。

SAE J1939 介紹

SAE J1939 協定由美國汽車工程師協會（society of automotive engineers，SAE）制定。其中的一些特性在於：

  • 使用 29 位元的擴充識別碼（extended identifier）。
  • 使用 CAN 2.0，傳輸速率為 250 kbps 或 500 kbps。(*)
  • 具有點對點定址（節點定址）和全域定址（訊息定址）。
  • 多封包訊息最多可傳輸 1785 位元組。
  • 以自己的網路管理控制網路存取。
  • 用於整體車輛通訊的標準化訊息。
  • 允許特定於製造商的訊息定義。
  • 定義自己的診斷介面。

J1939 幾乎都用擴充幀通訊，識別碼從原本的 11 位元長到 29 位元，多出來的空間可以在識別碼欄位裡直接放優先權、資料頁、群組編號等參數。

SAE J1939/14 物理層標準 首次發布於 2011，定義了 500 kbps 的速度。 SAE J1939/22 CAN FD 資料連結層 定義了 CAN FD 作為 J1939 的資料連結層實現，在現實生活中（≈2024），多數採用的還是 CAN 2.0 作為標準的傳輸層。

封包格式

SAE J1939-21 規範定義了 29 位元 CAN ID 如何規劃，如下表所示一共為 29 個位元：

Parameter group number (PGN)
PriorityExtended Data PageData PagePDU FormatPDU SpecificSource Address
AbbreviationPEDPDPPFPSSA
Bit Length3 bits1 bit1 bit8 bits8 bits8 bits

  • Priority：使用 3 個位元確定訊息在網路傳輸中的優先權，數值越低優先權越高，範圍為 0 到 7。所有控制相關訊息的預設優先權為 3，對於其他資訊、專有、請求和確認訊息的預設優先權為 6。當 PGN 被加入到應用層規範時，會為其分配一個建議值，優先權也可以依 OEM 的需求調整。

  • Extended Data Page：EDP 與 DP 一起用於確定 CAN ID 的結構。在 SAE 規範中，EDP 的預設初始值為 0。而對於其他協定如 ISO 11992，則會將 EDP 與 DP 同時設為 1，以區分 J1939 封包格式與其他協定的格式，並且後續的格式可以不遵循 J1939 的格式。

  • Data Page：與 EDP 一起用於確定 CAN ID 結構。並可整理為以下定義：

    EDPDP描述
    00SAE J1939 / ISO 11783（第 0 頁）PGNs
    01SAE J1939（第 1 頁）PGNs，NMEA 2000® 亦沿用此頁
    10SAE J1939（保留供未來使用）
    11ISO 11992 診斷（非 J1939 布局！）

  • PDU Format：一個 8 位元的欄位，用來決定 PS 的格式。範圍為 0 ~ 255。

  • PDU Specific：

    • 當 PF < 240 時，PS 為目標地址（destination address，DA），即將該封包傳遞給特定的目標位置，這也稱為 Specific PGN 或是 PDU1。其中，若 DA 為 0xFF（255），則為標準保留的全域位址（global address），會讓這個原本指定目標的封包送達網路上所有節點。
    • 當 PF ≥ 240 時，PS 為群組延伸（group extension），表示訊息為廣播訊息，又可稱為 Global PGN 或是 PDU2。

  • PGN 總共為 18 個 bit，由 {EDP, DP, PF, PS} 組成。

    PGN 用來辨識參數群組號，角色等同於非擴充幀裡的 CAN ID。在非擴充幀中，0x100 可以代表車速、0x101 代表引擎狀態；換到 J1939，就是由 PGN 告訴你這則訊息的類型與內容。

  • Source Address：網路上每個 SA 只會對應一個裝置，CAN ID 也才不會重複。SAE J1939-81 定義了防止 SA 撞號的位址宣告步驟。

由上述可以得知 PGN 一共有：

  • PF < 240 ：240 個
  • PF ≥ 240 ：16 × 256 個（PF 240 ~ 255，並對應 256 個群組延伸）

再加上 EDP 與 DP 可以組成為 00, 01 兩頁，所以最多可以有：[240 + (16 × 256)] × 2 = 8672 個 PGN

資料如何被定義與解碼？

資料怎麼定義、怎麼解碼，SAE 寫在 J1939-71 裡。定義的單位是疑似參數編號（suspect parameter number，SPN）。

SPN 的用途是給每一個車輛參數一組標準化的編碼，讓不同品牌、不同型號的 ECU 交換資料時不會有解讀上的歧義。有了這層標準化，跨廠牌的診斷、維修與車隊管理才做得起來。

SPN 會定義一個參數，該參數包含名稱、縮放係數（scaling factor）、偏移量（offset）、範圍、標籤與單位等屬性；至於資料長度與資料類型，則由對應的 PGN 封裝格式所決定。

以引擎速度為例子，J1939 定義了 PGN 61444 為電子引擎控制器 1（electronic engine controller 1，EEC1），優先權為 3，資料長度為 8 bytes。傳送週期則是「隨引擎轉速變動（engine-speed-dependent）」，以時間為基準時，標準定義的正常更新率為 20 ms（J1939-71 §5.1.7.2）；常見資料寫的 50 ms 是二手來源的簡化，可能與 EEC2／PGN 61443 混淆。

每個 SPN 定義了名稱、倍率（factor）和位移量（offset）。讀取到的原始值（RAW 值）可以透過這些定義轉換為實際數值。

例如，引擎轉速（engine speed）總共為 16 bits，若讀取到的原始值為 17214，則引擎的轉速為 2151.75 RPM（該標準中定義的上限值為 64255，即 8031.875 RPM）。

這些資訊最終會被整理成 DBC 檔案，用於描述這些參數，可於某些特定軟體載入，並會將錄製到的參數數值自動解碼並轉換。

最後，一個 SPN 可以存在於多個 PGN 中。例如，廠商自己定義 SPN 30000 代表韌體資訊，在出廠前中可以透過 PGN 2000 讀取和寫入該 SPN。而產品出廠後，限定只能透過 PGN 20000 來讀取這個數值。

SPN 中文常譯為疑似參數識別碼。在故障碼（diagnostic trouble code）中，SPN 用來指向「疑似故障的參數／元件」，這也是名稱裡 Suspect 的由來。不過要釐清的是：SPN 只有單一命名空間，是 SAE 為每一個參數（量測值、狀態、命令、協定內部資訊）指派的通用識別碼。同一個 SPN 會同時出現在正常資料 PGN（例如 SPN 110 引擎冷卻液溫度，每秒廣播一次）與故障訊息（DM1／DM2，搭配 FMI）中，它並不是和量測參數分開的「故障專用 ID」，量測值與疑似異常用的是同一個編號。

訊息類型

SAE J1939/21 目前記錄了總共五種訊息類型。它們是：

  • 命令（command）
  • 請求（request）
  • 廣播/回應（broadcasts/responses）
  • 確認（acknowledgement）
  • 群組功能（group functions）

命令

命令訊息類型實際上只是一個普通的 PGN，支援兩種 PDU 格式，PDU1 用於點對點通訊，PDU2 用於廣播通訊。命令類型的例子包括"變速器控制"、"地址請求"、"扭矩/速度控制"等...。

請求

PGN 為 0x0EA00。請求訊息類型被用於全域或從指定目標請求特定資料（PGN），其定義如下圖所示：

當接收端收到請求時，必須作出回應，即使這意味著在請求的 PGN 不存在時需要發送否定確認（NACK）。然而，當某個特定 PGN 不被支援時，全域請求不會觸發 NACK。

廣播/回應

廣播/回應訊息類型只是一個普通的 PGN，支援兩種 PDU 格式，PDU1 用於點對點通訊，PDU2 用於廣播通訊。它可以是未經請求的資料廣播，也可以是對命令或請求的回應。

確認

PGN 為 0x0E800。這是發送端與回應端之間的握手機制，用來確認命令或請求真的被處理了。

SAE J1939/21 標準中並沒有明確說明確認訊息只能支援 PDU1 格式。實務上 DA 可以設定為 0xFF，接收端過濾資料就簡單一些。

ACK 分為四種，由首個位元組判別：

  • Byte 0 = 0x00，Positive Acknowledgement (ACK)
  • Byte 0 = 0x01，Negative Acknowledgement (NACK)
  • Byte 0 = 0x02，Access Denied (有支援 PGN，但因安全原因拒絕存取)
  • Byte 0 = 0x03，Cannot Respond (有支援 PGN，但 ECU 無法回應。請稍後請求資料)

群組功能

用於廠商自訂或特別分配的 PGN，涵蓋專有功能、網路管理與多封包傳輸。

PGN 範圍：

  • 0x0EF00（61184），Proprietary A
  • 0x1EF00（126720），Proprietary A2
  • 0x0FF00（65280） ~ 0x0FFFF（65535），Proprietary B

要提醒的是：J1939-21 有定義 Proprietary A／A2／B，但並沒有官方的「Proprietary B2」。0x1FF00 ~ 0x1FFFF（130816 ~ 131071）確實保留給專有用途，但它只是 Proprietary B 在 Data Page 1 的對應範圍（CSS Electronics 稱為「Proprietary B – Page 1」），標準並未替它取名 Proprietary B2。A2 是正式名稱、B2 不是，這個不對稱就是線索。

傳送超過 8 個位元組

在傳統 CAN 中，資料長度僅能放入 8 個位元組。在 SAE J1939-21 定義了多幀傳輸方法，以傳輸超過 8 個位元組的資料長度，最多至 1785 個位元組。

在 J1939 通訊協定中，有兩種主要方法處理多幀資料傳輸：點對點訊息和廣播訊息：

  1. 請求傳送/允許傳送（RTS/CTS）： 使用 RTS/CTS 方法時，發送端會發送請求傳送（RTS）訊息給接收端，詢問是否可以傳送資料。接收端回應允許傳送（CTS）訊息表示可以接收資料。此方法為點對點的傳輸方式。
  2. 廣播宣告訊息（BAM）： 使用 BAM 方法時，發送端會廣播一個宣告訊息，表示接下來將會有多個資料幀傳送。這種方式不需要接收端的回應，適合廣播給多個接收端。

要用哪一種方法傳輸，由通訊協定 - 連接管理（transport protocol – connection management，TPCM）決定，資料則由通訊協定 - 資料傳遞（transport protocol – data transfer，TPDT）負責搬。

兩者對應的 PGN 分別為 TPCM：0x0EC00（60416）與 TPDT：0x0EB00（60160）。

TPCM

TPCM 中的 Byte 0 根據不同數值代表此封包的差異。

符號名稱 (PCAN)Byte 0封包說明
TPCM.RTS0x10 (16)連接模式請求發送
TPCM.CTS0x11 (17)連接模式準備發送
TPCM.EoM_ACK0x13 (19)訊息結束確認
TPCM.ConnAbort0xFF (255)連接中止
TPCM.BAM0x20 (32)連接模式廣播公告訊息

TPDT

TPDT 中的 Byte 0 用來表示序號，範圍從 1 到 255。後續的 7 個位元組用來傳遞資料，在傳遞很長的資料時，如果未滿足 7 的倍數，則使用 0xFF 補滿。

總共 255 個序號，每次傳遞 7 個位元組，總共最多傳遞 1785 個位元組的資料。

TPCM.RTS

RTS 訊息通知網路上的某個特定節點，希望與其建立虛擬連接。RTS 訊息的 SA 會設定為發送端的地址，DA 會設定為訊息的預期接收端地址，傳遞資料內容則為訊息長度、或是所請求的 PGN 編號。

TPCM.CTS

用來回應 RTS 的訊息。CTS 訊息會通知發送端已經準備好接收一定數量的資料。

TPCM.EoM_ACK

由接收端回傳給發送端，表示整個訊息正確並在接收端重組。

TPCM.ConnAbort

發送端或接收端都可以發送，用於未完成訊息傳輸的情況下關閉連接或防止連接初始化。封包裡面帶有中斷原因。

中斷代碼連線中斷原因
0保留給 SAE 指派。
1已在一個或多個連線管理會話（connection managed session）中，無法支援另一個。
2系統資源被用於其他任務，因此終止了此連線管理會話。
3發生逾時，這是中止連線以關閉會話。
4當資料傳輸進行時收到 CTS 訊息。
5達到最大重傳請求限制。
6意外的資料傳輸封包。
7錯誤的序列號（軟體無法復原）。
8重複的序列號（軟體無法復原）。

10–249保留給 SAE 指派。
250如果中止連線原因未列於表中，請使用代碼 250。

代碼 1~8 是實務上真正會遇到、且各家來源一致的部分。代碼 9 則是各方資料分歧之處，有些舊表會寫成「總資料長度大於 1785 位元組」，但這並不精確。1785 其實是 TP.CM_RTS／TP.CM_BAM「總長度欄位」的合法性檢查（必須落在 9 ~ 1785），違反時確實會中止連線，但並沒有被標準化成中止代碼 9。在 J1939-21／ISO 11783-7 的延伸傳輸協定（ETP）中，代碼 9 是「unexpected EDPO packet」。所以我會把代碼 9 視為保留／實作相依，不建議依賴它。

TPCM.BAM

BAM 不指定 DA，故 DA 為 0xFF，廣播給網路上所有節點。因為不需要 ACK 確認，傳遞流程比 RTS/CTS 單純。

DA 須為 0xFF (255)，表示為全域廣播。

封包傳遞分析

用雙通道 CAN 就能自發自收。這邊只討論 DP 為 0 的情況，但要知道 DP 可以為 1 表示為擴充 PGN。

單幀訊息傳遞（single-frame）

傳遞的資料內容，其長度 ≤ 8 個位元組。PGN 0xEF00 可以點對點也可以全域廣播，PGN 0xFF00 到 0xFFFF 則是全域廣播。

封包傳遞內容如下：

Time Diff (ms)SymbolPGNHex Data
0PropA0xEF0001 02 03 04 05 06 07 08

這邊在驗證上發現即使指定 DA，如果資料長度 ≤ 8 個位元組，則接收端還是會解此封包，不確定是 PCAN 實作上的差異。不過長度若超過 8 個位元組，由於 DA 不一致所以接收端不會處理該封包。

多幀訊息傳遞（multi-packet）

傳遞的資料內容，其長度大於 8 個位元組。又可分為廣播與點對點。

BAM 是廣播給所有節點，封包傳遞內容如下，假設傳遞 15 個位元組：

  1. BAM

    BAM 傳遞間隔為 50 ms 到 200 ms [*]，接收端的封包時間差最多為 750 ms。若超過此時間差並預期還有更多封包但未收到，則視為超時並自動關閉連接。

從表格中得知，控制值為 0x20，表示為 BAM，資料長度為 0x000F，即 15 個位元組，封包數量為 0x03。後續的 TPDT 封包首位元為序號，後面帶有實際資料。若最後一個封包的資料不足 7 的倍數，則補上 0xFF。

  • 依 SAE J1939-21，BAM 的 TP.DT 封包間隔為 50 ms 至 200 ms（下限 50 ms），這也是 PCAN 與多數實作採用 50 ms 的原因；接收端的 T1 逾時為 750 ms。

  1. P2P

    P2P 傳遞資料之前，兩端要先聲明位址。若未事先聲明，資料無法正常傳送，還可能因為沒送達而重發，增加網路負荷與延遲。

流程從握手開始：RTS (0x10) 封包發送給 DA 247，247 回傳 CTS 封包，表明可接收封包數量為 0x03，並指定下一個封包的序號為 0x01。之後開始傳遞資料，完成後由 247 發送 ACK 封包，確認收到的資料長度和封包數量。

如果資料長度或接收間隔時間太長（超過 750 ms），會導致接收方發送超時（timeout）訊息，並要求重新傳輸資料。此時，接收方會傳送 TPCM.CTS 給發送端，請求特定序列號的封包以防止會話中止。

這裡還有一個不太明顯的失敗情境。如果發送端太慢，接收端會在 TP.DT 傳送途中就超時，發出 TPCM.CTS 要求重傳，而這個 CTS 又被發送端收到。此時會話已經建立，就會中斷（原因：Multi_CTS）。解法是讓發送端在 750 ms 超時之前把資料送完，只要趕在重傳 CTS 送達之前傳完所有封包，會話就會順利跑到結束。

RTS 沒收到回應時，發送端會重試，每次間隔約 50 ms。如果 1300 ms 內都沒有回應，就發送 TPCM.ConnAbort 封包中止連接，然後再試一次 RTS。實測到的紀錄裡，這個過程重複最多 3 次。

補充對照標準：這個約 1300 ms 才中止，其實對應到標準化的 T3 = 1250 ms 發送端回應逾時（發送端送出 RTS／最後一筆資料後，最多等 T3 沒收到 CTS／EoM_ACK 就中止，多出來的約 50 ms 是量測與實作的誤差）。但每次約 50 ms 的重傳間隔與「最多 3 次」則是 PCAN 的實作行為，J1939-21 並沒有規定固定的重傳間隔或重傳次數，別把這兩個當成通用規則。

結論

這篇整理了 SAE J1939 的識別碼與 PGN 結構、SPN 怎麼定義與解碼、五種訊息類型，以及資料長度在 8 個位元組以內與以上時的處理方式。摸熟 J1939 之後，再回頭看 CANopen、AUTOSAR、NMEA 2000 這些協定，會發現底層的想法很接近。

網路管理（network management）、位址宣告（address claiming）、診斷（diagnostics）這幾塊還沒寫到，之後有機會再談。上面的內容拿來讀懂並解碼實車上的 J1939 流量已經夠用。

想再往韌體實作走，Open-SAE-J1939 是可以參考的專案，不過把現成的協定堆疊接進實際產品又是另一回事。
