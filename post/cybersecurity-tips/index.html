從 Wi-Fi 密碼到網站漏洞：常見資安風險與防範措施

從 Wi-Fi 弱密碼、網域控管腳本、WinPE 繞過登入，到未加密 Cookie 與 API 驗證缺陷，用實際案例講幾種臺灣最常見的入侵手法，以及對應的防護做法。

前言

網路安全（cybersecurity）對企業和個人都是躲不掉的議題，但在臺灣，很多公司、機構甚至個人使用者還是忽略了基本的資安防護，讓駭客能輕鬆入侵系統、竊取機密資訊，甚至讓業務癱瘓。

常見的資安漏洞其實不需要多高深的駭客技術，多半是基本防護意識不足，攻擊者才能輕易突破。這篇會談臺灣最常見的幾種攻擊手法，包括弱密碼攻擊、Cookie 權限提升、網站 API 漏洞。

這些手法看起來簡單，但往往就是資安意識不夠、防護不完整，才變成嚴重的漏洞。以下內容都來自實際案例與觀察。

Wi-Fi 密碼安全風險

臺灣許多企業與公共場所的 Wi-Fi 密碼設定過於簡單且可預測，使駭客無需使用暴力攻擊（brute-force attack）或進階攻擊技術，即可輕易入侵內部網路。

主要風險點：

  1. 可預測密碼（如 12345678、88888888）。
  2. 公司/市內電話。
  3. 統一編號（unified business number，UBN）。
  4. 個人手機號碼。

弱密碼很容易被字典攻擊破解；公司資訊、個人手機號碼這類，攻擊者也能靠公開資料查詢或社交工程拼出來。所以建議加上特殊符號，或改用更長、好記的可讀式密碼。

例如某 A 公司的密碼可以設為：

1

Thisispasswordforacompany2025$

或是家裡的密碼，可以設定為手機+特殊符號+單詞：

1

0910000123@home

較長又好讀的密碼能明顯降低被破解的風險，也遠比純數字密碼安全。

完全隨機的密碼（如 ^Wa091UW!N@U123QQ-USA）安全性最高，但一般使用者難輸入也難記，實際上反而不好用。

網域控管自動化腳本漏洞

公司 MIS 工程師管理使用者電腦時，通常會用 網域控管（domain management） 統一管理與設定權限，並即時監控使用者的行為，例如 登入 IP 位址、連線狀態、存取紀錄 等。

這些自動化腳本通常放在特定的網域網址上，用 Autoruns 檢查電腦開機時執行的腳本，就能辨識並找出伺服器路徑。

部分漏洞來自系統把 Administrator 帳號的密碼明文存在伺服器上，又沒做好加密與存取控制。

1
2

net user Administrator /active:yes
net user Administrator XXXXXXXXX

只要拿到這個檔案，就能解析出本機最高權限使用者的密碼，把自己在該電腦上的存取權限一路拉高。

有些 MIS 為了簡化管理，會把需要管理權限的安裝檔案獨立打包，讓一般使用者自行安裝。

這種打包的執行檔可以用 Win32 API 提權，或把改密碼的腳本封裝進可執行檔，執行時在系統特定位置解包腳本，跑完再自動刪掉。這類機制一旦沒管好，就會留下安全風險。

使用 WinPE 繞過登入限制並獲取最高權限

想拿到電腦的最高權限或存取硬碟檔案，只要 Windows 沒啟用 BitLocker，就能用 WinPE（如 USBOX 7.0）這類工具進系統，直接改或抽出檔案。

用 WinPE 進系統後，開啟命令提示字元，先備份放大鏡（Magnify.exe），再把它換成命令提示字元（cmd.exe）。

1
2
3

cd C:\windows\system32
ren Magnify.exe Magnify.back
copy cmd.exe Magnify.exe

重新啟動電腦並進入Windows 登入畫面，點選右下角的輕鬆存取，選擇並啟動放大鏡，此時系統將開啟cmd.exe，並以SYSTEM 權限執行。

接著，執行以下指令來啟用本機 Administrator 帳號，並將密碼設定為 MY_NEW_PASSWORD：

1
2

net user administrator /active:yes
net user administrator MY_NEW_PASSWORD

成功後，復原系統檔案：

1
2
3

cd C:\windows\system32
del Magnify.exe
ren Magnify.back Magnify.exe

重新啟動並以 administrator 登入，就能做你想做的事了。

重開機前記得確認系統有沒有寫入相關腳本，有些腳本會在登入時把 Administrator 底下的所有使用者清掉，所以建議斷網操作。

要擋掉這種用 WinPE 讀系統檔案的方式，啟用 BitLocker 加密就能讓 WinPE 讀不到磁碟內容。

Cookie 驗證漏洞

部分網頁使用 Cookie 驗證使用者的登入狀態，為資安漏洞的一環。

先前《CVE-2024-9970: NewType FlowMaster BPM Plus 系統的權限提升漏洞分析》裡提過，某系統用 Cookie 驗證身分，使用者 ID 以 Base64 編碼存在 Cookie 裡。因為沒做好驗證與防範，攻擊者只要改 Cookie 裡的 ID，就能冒充別的使用者。

大多數實作的流程如下：

  1. 使用者登入驗證：使用者提交憑證（如帳號密碼），伺服器驗證後產生唯一的 session token 或 JWT，token 內可能帶有使用者 ID 及其他身分資訊。
  2. 憑證處理與傳送：伺服器把 token 用 Cookie 送到用戶端。現代的安全實作會把 Cookie 內容加密或數位簽章，防止竄改。
  3. 後續請求驗證：使用者瀏覽器在後續請求中自動帶上 Cookie，伺服器再依 token 的合法性、完整性與有效性確認使用者身分與權限。
  4. 安全屬性設定：為了防跨站腳本攻擊（cross-site scripting，XSS）這類風險，通常會在 Cookie 上設 HttpOnly 與 Secure 屬性，讓只有伺服器能讀，而且只在加密通訊下傳輸。

這個網站會寫入 ASP.NET_SessionId 的 Cookie，這是 ASP.NET 內建 Session 管理機制自動產生與管理的，但它最終的實作卻自己引入了安全漏洞。

Cookie 攻擊技術解析

使用者在網頁登入後，伺服器與用戶端就靠 Cookie 驗證身分，這個 Cookie 等於一張數位身分證。攻擊者只要偷到它，就能偽造身分、繞過密碼驗證，存取受保護的系統資源。

取得使用者的 Cookie 有很多辦法，例如：

  1. 用瀏覽器擴充功能匯出、匯入
  2. 中間人攻擊（man-in-the-middle, MiTM）
  3. 跨站腳本（XSS）攻擊
  4. 本機存取或相關工具
  5. 其他....

大多數網站不會主動驗證使用者的裝置與環境變化，所以 Cookie 被偷走時往往很難察覺。為降低 Cookie 外洩風險，必須確保裝置僅由本人使用，避免未授權存取。進階一點的防護是裝防毒軟體，擋掉惡意程式竄改系統根憑證，避免敏感資料被攔截或竊取。

不安全的 API 驗證機制會引發未授權存取與資料竄改的風險

API 設計上，有些網站太相信用戶端送來的憑據，後端沒做嚴格驗證，攻擊者就能繞過身分驗證，做未授權存取或資料竄改，嚴重影響系統安全。

這類 API 請求可以用 Fiddler AutoResponder 或瀏覽器內建的 開發人員工具 攔截、修改，在本機覆寫請求或回應來左右伺服器端的處理結果，形成安全風險。

要顧好 API 的安全，應該做到以下幾點：

  • 後端驗證：所有請求都由伺服器完整驗證，不能只靠用戶端送來的憑據。
  • 請求簽章：用 HMAC、JWT 或其他加密機制保護 API 請求的完整性與合法性，防止請求被竄改。
  • 回應完整性驗證：對回應資料做完整性檢查，避免攻擊者攔截後改掉回應內容來騙過系統。

以下三個可能的 API 安全缺陷案例供參考：

API 驗證機制漏洞導致未授權權限提升

某網站的登入機制靠後端 API 驗證身分，再依回傳結果開啟特定功能。問題是頁面要顯示什麼完全看 API 回應，攻擊者只要攔截並改掉 API 回應，就能拿到未授權的管理員權限，造成 權限提升 或 資料洩露。

API 參數驗證缺失導致價格竄改漏洞

在某訂餐平台，使用者把商品加入購物車時，前端會向 API 發送請求，帶著 金額、商品 ID 等資訊。這個 API 沒對金額參數做伺服器端驗證，也沒加密請求內容，攻擊者攔截 API 請求後就能手動改掉商品價格，用低於實際售價的金額完成交易，造成營收損失。

郵件 API 欄位驗證不足導致寄件人偽造漏洞

某網站的「匯出報表」功能讓使用者用 API 把報表寄到指定信箱。原始設計中，API 預設寄件者是 admin@google.com，收件者由使用者指定。但這個 API 讓用戶端直接提交寄件者與收件者的電子郵件，後端又沒限制寄件者欄位不能改，攻擊者就能偽造寄件人身分，冒充任意郵件地址發送惡意郵件。

這幾個案例都說明 API 驗證機制一薄弱，風險就很嚴重。企業設計 API 時至少要做到：

  • 驗證機制嚴謹，避免憑據被竄改、身分被偽造。
  • 請求與回應的完整性受保護，防範惡意資料竄改。
  • 關鍵參數不可由用戶端直接控制，降低業務風險與攻擊面。

結論

駭客手法一直在進步，但很多企業與個人還是忽略基本資安防護，系統就容易被打進來。弱密碼、網域控管漏洞、Cookie 權限提升、API 驗證缺陷這些問題，說到底都是資安意識不足、防護機制不完整。

想降低風險，可以從這幾件事做起：

  1. 強化身分驗證：用強密碼，開 雙因素驗證（2FA），避免帳戶被盜用。
  2. 顧好網域與權限：加密管理腳本，限制高權限帳戶存取，擋掉未授權操作。
  3. 管好 Cookie 與會話：設定 HttpOnly、Secure，加上 Session Timeout，降低憑證被竊取的風險。
  4. 永遠不要信任用戶端傳來的資料：所有來自用戶端的輸入（API 請求、Cookie、URL 參數、表單資料等）都要在伺服器端驗證與過濾，防範 SQL 注入、XSS、權限提升等攻擊。
  5. 選安全一點的系統方案：別用 低成本、沒技術支援 的系統，並定期做安全測試。
  6. 啟用 BitLocker 加密：擋掉 WinPE 或實體存取 偷走磁碟資料。

資安是要長期經營的，定期檢測漏洞、盯著異常行為，比事後補破網省事得多。
