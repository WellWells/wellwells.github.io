SAE J1939 Protocol: Introduction and Packet Analysis

What SAE J1939 adds on top of CAN: the 29-bit ID layout, how PGNs and SPNs define and decode data, the five message types, and how RTS/CTS and BAM move payloads past 8 bytes.

Introduction

In my previous article, Characteristics and Key Points of Controller Area Network (CAN bus), I went through the basics of CAN: its variants, the differences between them, and the layout of a data frame.

Traditionally, the way I transfer data over CAN is by agreeing on a specific ID and deciding what each of the 8 data bytes means, then documenting all of it in a DBC file so the receiver can decode it back.

The catch is that CAN itself only defines how bits move across the bus. It says nothing about what those bits mean or how they should be structured. That gap is exactly why higher-level protocols (HLPs) exist. Depending on the application, you might reach for CCP/XCP, CANopen, AUTOSAR, or—the subject of this post—J1939.

As an example without any HLP: I might decide that on ID 0x100, the first 4 bytes are vehicle speed (0–150 km/h) and the last 4 bytes are gear state, where 1000 means P and 0100 means D. Every vendor invents their own mapping, and it usually ends up in a giant Excel sheet or a DBC file that explains how to decode each signal. J1939 replaces that ad-hoc mess with a standardized scheme.

Introduction to SAE J1939

J1939 is developed and maintained by the Society of Automotive Engineers (SAE), a US-based standards organization. The features I care about most are:

  • A 29-bit extended identifier (CAN 2.0B).
  • Built on CAN 2.0, with a bus speed of 250 kbps or 500 kbps.(*)
  • Both point-to-point addressing (node addressing) and global addressing (message addressing).
  • Multi-packet messages of up to 1785 bytes.
  • Network access control handled by its own network management.
  • A standardized message set for vehicle-wide communication.
  • Room for manufacturer-specific message definitions.
  • Its own diagnostic interface.

Because J1939 communicates almost entirely with extended frames, the identifier grows from 11 bits to 29 bits. That extra room is what lets J1939 pack metadata—priority, data page, the parameter group number, and so on—directly into the ID field.

SAE J1939/14 (Physical Layer), first published in 2011, defines the 500 kbps physical layer. SAE J1939/22 (CAN FD Data Link Layer) defines a CAN FD-based data link layer for J1939. In practice (as of ~2024), most production networks I've seen still run classic CAN 2.0.

Packet Format

SAE J1939-21 specifies how the 29-bit CAN ID is laid out. All 29 bits break down like this:

Parameter Group Number (PGN)
PriorityExtended Data PageData PagePDU FormatPDU SpecificSource Address
AbbreviationPEDPDPPFPSSA
Bit Length3 bits1 bit1 bit8 bits8 bits8 bits

  • Priority: 3 bits that set the message priority during bus arbitration. A lower value means higher priority, and the range is 0 to 7. Control-related messages default to priority 3; other informational, proprietary, request, and acknowledgment messages default to 6. When a PGN is added to the application-layer spec it gets a recommended value, and an OEM can still tune it to fit their needs.

  • Extended Data Page (EDP): works together with DP to define the structure of the CAN ID. For ordinary J1939, EDP defaults to 0. Other protocols reuse this bit to break away. For example, ISO 11992 sets both EDP and DP to 1 so its frames can be told apart from J1939 and follow a non-J1939 layout from that point on.

  • Data Page (DP): paired with EDP to select the ID structure. The four combinations are:

    EDPDPDescription
    00SAE J1939 / ISO 11783 (Page 0) PGNs
    01SAE J1939 (Page 1) PGNs, also used by NMEA 2000®
    10SAE J1939 reserved (for future use)
    11ISO 11992 diagnostics (non-J1939 PGN layout)

  • PDU Format (PF): an 8-bit field (0–255) that, together with the next field, decides how PS is interpreted.

  • PDU Specific (PS):

    • When PF < 240, PS is the Destination Address (DA): the frame is aimed at one specific node. This is called a Specific PGN or PDU1. If DA is 0xFF, it's the reserved Global Address (255), which makes the (otherwise addressable) frame reach every node on the bus.
    • When PF ≥ 240, PS is a Group Extension. The frame is a broadcast. This is called a Global PGN or PDU2.

  • PGN: 18 bits total, made up of {EDP, DP, PF, PS}.

    The PGN is what identifies a parameter group. It plays the same role in J1939 that the CAN ID plays in a plain (non-extended) network: just as you might let 0x100 mean vehicle speed and 0x101 mean engine status, the PGN tells you the type and content of a J1939 message.

  • Source Address (SA): on any given bus, one SA maps to exactly one device, which is what keeps each CAN ID unique. SAE J1939-81 defines the address-claiming procedure that prevents two nodes from grabbing the same SA.

From the structure above, the PGN count works out to:

  • PF < 240: 240 PGNs
  • PF ≥ 240: 16 × 256 PGNs (PF 240–255, each with 256 group extensions)

Add the DP bit (which gives Page 0 and Page 1) and you get a maximum of [240 + (16 × 256)] × 2 = 8672 PGNs.

Some of that space is already allocated by SAE (engine data and so on), and some is left open for manufacturers. Here's how the ranges split:

How is Data Defined and Decoded?

SAE spells out how the data inside each message is defined and decoded in SAE J1939-71 (these days the full parameter catalog also lives in the J1939-DA Digital Annex). The unit of definition is the SPN (Suspect Parameter Number).

The point of the SPN is to give every vehicle parameter one standardized encoding, so that ECUs from different brands and models can exchange and interpret data without ambiguity. That standardization is what makes cross-vendor diagnostics, maintenance, and fleet management practical in the first place.

An SPN defines a parameter's name, scaling factor, offset, valid range, label, and units. The data length and data type, however, come from the PGN that carries it.

Take engine speed as an example. J1939 defines PGN 61444 as Electronic Engine Controller 1 (EEC1): default priority 3, data length 8 bytes, and a transmission rate that is engine-speed-dependent (the standard's normal time-based update rate is 20 ms—it is not a flat 50 ms, which is a figure I often see repeated by secondary sources, possibly confused with EEC2/PGN 61443).

Here's how its 8 bytes are carved up, with each SPN mapping to a specific signal:

Each SPN carries its own name, factor, and offset, and that's all I need to turn a raw value back into a real-world number.

For instance, Engine Speed (SPN 190) is 16 bits with a factor of 0.125. If the raw value I read is 17214, the engine speed is 17214 × 0.125 = 2151.75 RPM. The operational maximum the standard defines is a raw value of 64255, which works out to 8031.875 RPM.

In practice all of this ends up in a DBC file describing every parameter. Load that file into the right tool and it will decode and scale the recorded values automatically.

One last thing worth knowing: the same SPN can live in more than one PGN. A vendor might define SPN 30000 as firmware information, make it readable/writable through PGN 2000 on the production line, and then lock it to read-only through PGN 20000 once the unit ships.

A quick note on the word "Suspect": there's only one SPN namespace, and the SPN is the universal SAE-assigned identifier for every parameter: measured values, statuses, commands, and internal protocol data alike. The exact same SPN appears in normal data PGNs (e.g. SPN 110, Engine Coolant Temperature, broadcast every second) and, when something goes wrong, in diagnostic messages (DM1/DM2) paired with a Failure Mode Identifier. The "Suspect" in the name comes from that diagnostic origin—the parameter suspected of being faulty—not from any distinction between a special "fault" ID and a regular "measurement" ID. It's the same number either way. (Even Vector notes the name is a little misleading.)

Message Types

SAE J1939-21 records five message types:

  • Command
  • Request
  • Broadcast/Response
  • Acknowledgement
  • Group Functions

Command

A Command is really just a regular PGN. It supports both PDU formats: PDU1 for point-to-point and PDU2 for broadcast. Typical examples are "Transmission Control," "Address Request," and "Torque/Speed Control."

Request

The Request uses PGN 0x0EA00 (59904). I use it to ask for a specific PGN, either globally or from one particular node:

When a node receives a directed request, it must respond, even if that means returning a Negative Acknowledgement (NACK) because the requested PGN doesn't exist. A global request, on the other hand, does not trigger a NACK for a PGN a node doesn't support; nodes simply stay quiet.

Broadcast/Response

Another plain PGN that supports both PDU1 and PDU2. It can be an unsolicited data broadcast, or a response to a command or request.

Acknowledgement

The Acknowledgement uses PGN 0x0E800 (59392). It's the handshake between the transmitting and responding nodes that confirms a command or request was actually processed.

J1939-21 doesn't strictly require the Acknowledgement to be PDU1-only, so in practice the DA can be set to 0xFF, which conveniently lets the receiver side filter less aggressively.

There are four ACK kinds, told apart by the first byte:

  • Byte 0 = 0x00 — Positive Acknowledgement (ACK)
  • Byte 0 = 0x01 — Negative Acknowledgement (NACK)
  • Byte 0 = 0x02 — Access Denied (PGN is supported, but access is refused for security reasons)
  • Byte 0 = 0x03 — Cannot Respond (PGN is supported, but the ECU is busy, try again later)

Group Functions

These cover manufacturer-defined and specially-assigned PGNs used for proprietary functions, network management, and multi-packet transport.

The proprietary ranges are:

  • 0x0EF00 (61184): Proprietary A
  • 0x1EF00 (126720): Proprietary A2
  • 0x0FF00 (65280) – 0x0FFFF (65535): Proprietary B

One caveat I want to flag: J1939-21 names Proprietary A, Proprietary A2, and Proprietary B, but it does not define an official "Proprietary B2." The range 0x1FF00–0x1FFFF (130816–131071) is reserved for proprietary use. It's simply the Data Page 1 equivalent of Proprietary B (CSS Electronics labels it "Proprietary B – Page 1"), not a separately named parameter group.

Transmitting Over 8 Bytes

A classic CAN frame can only hold 8 bytes. To move more than that, SAE J1939-21 defines a multi-frame transport protocol that scales up to 1785 bytes. There are two ways to do it—one point-to-point, one broadcast:

  1. Request to Send / Clear to Send (RTS/CTS): the sender first sends an RTS to ask whether it may transmit. The receiver answers with a CTS to say it's ready. This is the point-to-point method.
  2. Broadcast Announce Message (BAM): the sender broadcasts an announcement that several data frames are coming. There's no response from the receiver, which is exactly what makes it suitable for broadcasting to many nodes at once.

Which method is used is negotiated through Transport Protocol – Connection Management (TPCM), and the actual payload is carried by Transport Protocol – Data Transfer (TPDT).

Their PGNs are TPCM: 0x0EC00 (60416) and TPDT: 0x0EB00 (60160).

TPCM

In a TPCM frame, Byte 0 tells you what kind of control message it is:

Symbol Name (PCAN)Byte 0Description
TPCM.RTS0x10 (16)Request to Send (RTS)
TPCM.CTS0x11 (17)Clear to Send (CTS)
TPCM.EoM_ACK0x13 (19)End of Message Acknowledgment
TPCM.ConnAbort0xFF (255)Connection Abort
TPCM.BAM0x20 (32)Broadcast Announce Message (BAM)

TPDT

In a TPDT frame, Byte 0 is the sequence number, from 1 to 255. The remaining 7 bytes carry the actual data; if the final packet doesn't fill all 7, the leftover bytes are padded with 0xFF.

With 255 sequence numbers and 7 bytes each, the ceiling is 255 × 7 = 1785 bytes.

TPCM.RTS

The RTS tells one specific node that I'd like to open a virtual connection with it. The SA is my address, the DA is the intended receiver, and the payload carries the total message length and the PGN being transferred.

TPCM.CTS

The CTS is the reply to an RTS. It tells the sender the receiver is ready, and how many packets it's willing to accept right now.

TPCM.EoM_ACK

Sent by the receiver back to the sender once the whole message has arrived and been correctly reassembled.

TPCM.ConnAbort

Either side can send this to tear down an incomplete transfer, or to refuse a connection before it starts. The packet carries a reason code:

Abort CodeConnection Abort Reason
0Reserved for SAE assignment.
1Already in one or more connection-managed sessions; cannot support another.
2System resources were needed for another task, so this session was ended.
3A timeout occurred; aborting to close the session.
4A CTS was received while data transfer was already in progress.
5Maximum retransmit-request limit reached.
6Unexpected data-transfer packet.
7Bad sequence number (software cannot recover).
8Duplicate sequence number (software cannot recover).
9Reserved in the base transport protocol (see note below).
10–249Reserved for SAE assignment.
250Use code 250 when the abort reason isn't listed in the table.
251–255Per SAE J1939-71 definitions.

Codes 1–8 are the ones you'll actually hit in practice, and they're consistent across sources. Code 9 is where references disagree. Some older tables print it as "total message size > 1785 bytes," but that's not quite right. The 1785-byte ceiling is really a validity check on the total-message-size field inside TP.CM_RTS / TP.CM_BAM (it must be in the 9–1785 range); violating it does abort the session, but it isn't standardized as abort code 9. In the harmonized J1939-21 / ISO 11783-7 extended transport protocol, code 9 is "unexpected EDPO packet." I'd treat code 9 as reserved/implementation-dependent rather than rely on it.

TPCM.BAM

A BAM has no specific target, so its DA is 0xFF and it goes out to every node on the bus. Because no ACK is involved, the flow is simpler than RTS/CTS.

The DA must be 0xFF (255), marking it as a global broadcast.

Packet Transmission Analysis

With a dual-channel CAN setup I can have one channel transmit and the other receive, so I can watch my own traffic. Everything below assumes DP = 0. Just keep in mind DP can be 1 for the extended PGN page.

Single Frame Message Transmission

The payload here is ≤ 8 bytes. PGN 0xEF00 can be point-to-point or global, and PGNs 0xFF00–0xFFFF are global broadcast.

A captured exchange looks like this:

One thing I noticed while testing: even when I set a specific DA, the receiver still decodes a frame whose payload is ≤ 8 bytes—I suspect that's a quirk of how PCAN is implemented. Once the data goes over 8 bytes, though, a mismatched DA does cause the receiver to drop it.

Multi-Packet Message Transmission

When the payload is larger than 8 bytes, the transfer splits into either a broadcast (BAM) or a point-to-point (RTS/CTS) session.

For BAM, the data is broadcast to everyone. Here's a 15-byte example:

  1. BAM

    In a BAM session the transmitter spaces successive TP.DT packets 50 ms to 200 ms apart, and the receiver applies a 750 ms timeout. If more than 750 ms passes while it's still expecting packets, it treats the session as timed out and closes it automatically.

Time Diff (ms)SymbolPGNHex DataSADA
0TPCM.BAM0xEC0020 0F 00 03 FF FF FF 00248255

50TPDT0xEB0002 08 09 0A 0B 0C 0D 0E248255
50TPDT0xEB0003 0F FF FF FF FF FF FF248255

Reading the table: the control byte 0x20 marks this as a BAM, the data length is 0x000F (15 bytes), and the packet count is 0x03. Each TPDT then leads with its sequence number followed by the real data, and the last packet pads out to a multiple of 7 with 0xFF.

  • Per SAE J1939-21, a BAM session spaces its TP.DT packets 50 ms to 200 ms apart (50 ms minimum), which is why PCAN and most implementations use 50 ms; the receiver-side T1 timeout is 750 ms.

  1. Point-to-Point (P2P)

    Before a P2P transfer can happen, both nodes need to have claimed their addresses. Skip that step and the transfer won't go through cleanly. You end up retransmitting, which just adds bus load and latency.

The handshake comes first: an RTS (0x10) goes to node 247, and 247 replies with a CTS saying it can take 0x03 packets and wants the next one to start at sequence 0x01. The data then flows, and once it's done 247 sends an EoM_ACK confirming the total length and packet count it received.

If the data is large or the gaps between packets stretch past the 750 ms timeout, the receiver will flag a timeout and ask for a retransmit. It does this by sending a TPCM.CTS requesting the specific sequence number it's missing, which keeps the session alive instead of aborting it.

There's a subtle failure mode here. If the sender is too slow, the receiver may time out and fire off a TPCM.CTS retransmit request during the data transfer. When the sender then receives that CTS mid-flight, the (already-established) session aborts with reason "CTS while transferring" (Multi_CTS). The fix is simply to make sure the sender finishes the whole transfer before the 750 ms timeout—if it gets all the data out before that retransmit CTS arrives, the session runs to completion without interruption.

When the RTS gets no answer, the sender retries: each attempt waits about 50 ms, and if nothing comes back within ~1300 ms it sends a TPCM.ConnAbort and tries the RTS again. In my capture this repeats up to 3 times before giving up.

Worth tying this back to the standard: that ~1300 ms before the abort lines up with the standardized T3 = 1250 ms originator response timeout (the sender waits up to T3 for a CTS or EoM_ACK before aborting; the extra ~50 ms is measurement/implementation overhead). The ~50 ms retry spacing and the 3-retry cap, on the other hand, are PCAN-specific. J1939-21 doesn't mandate a fixed retry interval or a retry count, so don't read those as universal.

Conclusion

This was a walk through the core of SAE J1939: the ID and PGN structure, how SPNs define and decode data, the message types, and how the transport protocol handles payloads both under and over 8 bytes. Getting comfortable with J1939 also makes it much easier to pick up its relatives later, like CANopen, AUTOSAR, and NMEA 2000, since they share a lot of the same DNA.

I didn't cover everything: network management, address claiming, and diagnostics are all topics for another day. But what's here should be enough to read, decode, and reason about J1939 traffic on a real bus.

If you want to go further into firmware, projects like Open-SAE-J1939 are a good reference, though wiring an existing stack into a real product is its own kind of challenge.
