Deno Joins Cloudflare, and Official Runtime Development Ends in a Year

What the Deno-joins-Cloudflare announcement says: one more year of runtime maintenance, Deno Deploy closing in six months, celld merging into workerd, and why I moved back to Node.js.

On October 9, 2026, Deno creator Ryan Dahl announced on the Deno blog that the entire Deno team is joining Cloudflare. The team will support the Deno JavaScript runtime for one more year and then end its own development of it, while the project stays open source. I have already moved my Deno project back to Node.js, so the news was not a surprise. I still went through the official statements, Cloudflare's motives, and the current state of each runtime; the results are below.

What the announcement says

Cloudflare published a joint post the same day, signed by Ryan and Kenton Varda. It covers the merger of workerd and celld and does not say what happens to the Deno runtime. That is only in the Deno post.

ItemWhat the announcement says
Deno runtimeOne more year of support with monthly bug-fix and security releases, after which the Deno team ends its own development; the project stays open source and others are welcome to continue it
Deno DeployKeeps running for six months, then shuts down; paying customers moving to Cloudflare Workers get migration support
JSRKeeps running, with its infrastructure moving to Cloudflare
rusty_v8Remains supported, with work toward integrating it into workerd
Fresh, Deno SubhostingNot mentioned

The announcement does not say when the six months for Deno Deploy start; counting from October 9 puts the shutdown around April 2027.

Cloudflare wants celld

celld is an open-source project the Deno team released in August 2026. It is a single Rust binary licensed under Apache-2.0, and it runs a Cloudflare Workers app from your existing wrangler.json, Durable Objects included, on your own machines. Products that need the Cloudflare network, a GPU or a browser farm are out of scope.

A Durable Object is a Cloudflare Worker that combines compute and storage: each object has a globally unique name and private storage, and runs single-threaded. Cloudflare's open-source Workers runtime is workerd, but Kenton writes that workerd implements Durable Objects only as a single instance, "good enough for local testing, but unable to scale". Cloudflare therefore plans to merge code and ideas from celld back into workerd, with Ryan and Bert Belder leading the effort to make workerd self-hosting a first-class supported option.

The Deno post adds that the persistent state and WebSockets of Durable Objects suit agent harnesses, which is why celld focuses on them.

Developer tools that joined larger companies over the past year

Bun is, like Deno, a JavaScript runtime alongside Node.js, which makes it the closest parallel to Deno in this group. It joined Anthropic in December 2025 and states that it stays open source under the MIT license; Claude Code ships as a Bun executable. Astral, the developer of uv and Ruff, announced on March 19, 2026 that it had entered an agreement to join OpenAI's Codex team. The deal had not closed at the time, and I found no report that it has. Astro joined Cloudflare in January 2026 and also stays MIT-licensed. All of these say development continues, and the Deno runtime is the only one in this group where development is announced to end.

Downstream users are affected too. Supabase's docs say Edge Functions are developed with Deno, and Netlify's docs say Edge Functions run on a runtime based on Deno. As of October 10, I found no official response from either company to the announcement.

What Deno got right

Deno was created by Ryan, the original author of Node.js, and is built around a sandbox by default and running TypeScript without extra tooling. The items below are where I think Deno got there earlier; Node.js has since added matching features, at different levels of maturity.

FeatureDenoNode.js
Native TypeScriptBuilt inEnabled by default and stable; only strips types and does no type checking
Built-in test runnerDeno.testnode:test, stable
Compile to a single executabledeno compileSingle executable applications, Stability 1.1 (active development)
Permission controlSandboxed by default--permission is stable and has to be turned on

The executable row shows the widest gap: Node.js documentation still lists single executables as under active development, while deno compile is an ordinary CLI command. Together these features remove a bundler and a test framework from the dependency list, which is the part of Deno I rate highest.

The announcement says others are welcome to continue its development. Maintaining an entire runtime is a lot of work, and I do not expect anyone to take it over any time soon. Anthropic bought Bun, and OpenAI might pick up Deno someday, but that is purely my own guess.

Why I moved back to Node.js

In "2024 Developer Year-End Review" I wrote that I decided at the end of 2024 to move my personal projects from Node.js to Deno, PostgreSQL and Next.js. Development ran into a pile of compatibility problems that never appear on Node.js, and I describe two representative examples in "Mastering Agentic Workflow". Electron is tightly bound to Node.js, so using it with Deno made for a poor development experience, and switching to Tauri meant setting up a Rust toolchain first. Since moving back to Node.js, maintenance has run without any obstacles.

Deno's npm compatibility became stable only in 1.28 in November 2022, and Deno 2 in October 2024 went further with native support for package.json and node_modules. Next.js has gaps too: Deno's official Next.js tutorial requires four unstable settings in deno.json, and an experimental deno desktop for desktop apps was added only in Deno 2.9 in June 2026.

The risk of Bun switching languages

With Deno development ending, the alternatives among comparable runtimes are Node.js and Bun, and Bun has just changed its underlying language. Bun was originally written in Zig. On May 14, 2026 the pull request rewriting all of the Zig code in Rust was merged, and v1.4.0 on August 20 was the first Rust release. Bun's stated reason is that a large share of the v1.3.14 bug fixes were memory errors such as use-after-free and double-free, rooted in mixing garbage collection with manual memory management; its author Jarred Sumner says "I don't blame Zig for that".

The rewrite covers all of the Zig code; about 20% of Bun is C++, and libraries such as JavaScriptCore remain. For production use, replacing the language underneath a runtime is a risk in itself, and Bun says the rewrite introduced 19 known regressions, each of which has been fixed.

In its December 2025 announcement, Bun states that Anthropic uses it as infrastructure for Claude Code and the Agent SDK, and that it has been prioritizing issues from the Claude Code team for several months. Its roadmap says it will keep focusing on high-performance JavaScript tooling and Node.js compatibility. I have no evidence that Bun's general direction has shifted because of this, so I list it only as a risk item.

What I base the choice on

For production I pick Node.js, based on the State of JS respondent counts and Node.js's release rules. In the State of JS 2025 runtime section, the base is 11,141 respondents and Node.js has 10,062, or 90.3%. The base differs between years, so the table compares Deno and Bun by share:

YearBaseDeno respondentsDeno shareBun respondentsBun share

A Node.js long-term support (LTS) release typically guarantees critical bug fixes for a total of 30 months, and the official guidance is that production applications should use only Active or Maintenance LTS releases. As of October 10, v24 is Active LTS and v22 is Maintenance LTS. Node.js is also scheduled to move to one major release a year from 27.x, with every major release becoming LTS. The announcement says this schedule is not final, but as planned, upgrades can be scheduled ahead of time.

Projects already on Deno have a year of monthly updates, which is enough time to plan a migration. My own project stays on Node.js.
