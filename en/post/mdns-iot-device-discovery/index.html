How mDNS Works: Device Discovery in IoT

How mDNS and DNS-SD let IoT devices announce themselves: what makes .local special, the probing and announcing flow, an ESP32 plus Node.js implementation, and the Windows Firewall pitfall that swallows the responses.

Introduction

In traditional networks, connecting to a device like a printer usually requires a fixed IP from a DHCP server or a name resolution from a DNS server. But in the era of the Internet of Things (IoT), expecting home users to maintain DNS records is unrealistic. mDNS (Multicast DNS) was created to solve this: allowing devices to introduce themselves. It is the core technology behind Zero Configuration Networking (ZeroConf), enabling devices to automatically negotiate IPs and announce their names.

Why Do We Need mDNS?

Traditional DNS relies on central servers and static configurations, which struggle in home or small office networks where IPs change frequently and professional management is absent. When a new device comes online, DNS records are often not updated in time, leading to connection failures.

mDNS (RFC 6762) solves this with a decentralized design:

  • Decentralized: No central DNS server is needed; every device acts as its own name server.
  • Plug-and-Play: Devices announce themselves as soon as they connect and revoke their names when they go offline, requiring no manual setup.
  • Real-time Updates: Name resolution happens directly within the local network (LAN), making it fast and suitable for dynamic IP environments.

This mechanism is widely used in Smart Homes (HomeKit devices), Small Offices (Printers, NAS), and Ad-hoc Networks (Screen mirroring, file sharing).

Core Technology and How It Works

Standards and Implementations: Bonjour vs. Avahi

Open Standard (IETF), Bonjour (Apple), and Avahi (Linux) are often used interchangeably, but the distinction is simple: mDNS/DNS-SD are the protocol standards, while Bonjour and Avahi are software implementations on different operating systems.

  • mDNS (RFC 6762) / DNS-SD (RFC 6763): Communication protocols defined by the IETF.
  • Bonjour: Apple's implementation, built into macOS and iOS (and available as Print Services for Windows).
  • Avahi: The Linux implementation, widely used on Ubuntu, Raspberry Pi, and others. It is compatible with Bonjour.

This explains why an iPhone can easily discover a Raspberry Pi. They both speak the same mDNS language.

ZeroConf is a technology stack: the bottom layer uses IPv4LL to automatically obtain an IP (169.254.x.x), the middle layer uses mDNS for name resolution (Hostname -> IP), and the top layer uses DNS-SD for service discovery (Service -> Hostname). This vertical integration makes the process from connecting to being usable completely automatic.

Architecture: Decentralized P2P Queries

mDNS abandons the central server for a Peer-to-Peer (P2P) model. Every device is both a Client and a Server: it sends queries when it needs to resolve a name, and responds when it receives a query matching its own name.

  • IPv4 Multicast Address: 224.0.0.251
  • IPv6 Multicast Address: FF02::FB
  • UDP Port: 5353

Practical Limitations & Tips:

  • Cross-Subnet Issues (VLANs): Since multicast cannot cross routers (TTL=1), if you isolate IoT devices on a Guest Network (common in Unifi setups), you must enable an mDNS Reflector on your router so main network devices can find them.
  • Privacy Concerns: On public Wi-Fi, anyone can listen to mDNS broadcasts. Ideally, use AP Isolation on guest networks to protect privacy.

Domain Suffix: The Special Case of .local

.local is the top-level domain (TLD) reserved for mDNS. When an operating system sees a URL ending in .local (e.g., printer.local), it forces the system to bypass the configured DNS server and instead send a multicast query to the local network.

⚠️ Enterprise Network Warning

Never use .local as a domain name in Active Directory (AD) or enterprise internal networks (like corp.local). This causes macOS/Linux devices to prioritize mDNS resolution over querying the AD server, leading to severe connection delays or resolution errors. Use .intranet or .lan instead.

Communication Flow

mDNS queries are like shouting across an open office instead of looking up a phone number:

  1. Query: The Client broadcasts to 224.0.0.251:5353: "Who is printer.local?"
  2. Listen: All devices on the LAN receive this, but only the device with that name processes it.
  3. Response: The printer replies: "I am printer.local, my IP is 192.168.1.50."

Clarification: The router only forwards packets in this process; it does not record or resolve names.

Probing and Announcing

When a smart device (like an ESP32) connects to the network, it goes through two key phases to keep its name unique on the local link:

  • Probing Phase: The device sends at least 3 probe queries (spaced 250ms apart) asking: "Is anyone called printer.local?" If no one answers, it officially claims the name. This is crucial for avoiding name conflicts (recommended by RFC 6762).

  • Announcing Phase: Once the name is confirmed unique, the device sends an unsolicited announcement: "I am printer.local, and my IP is 192.168.1.100."

Handling Name Conflicts

According to RFC 6762, devices must handle conflicts as follows:

  • Automatic Renaming: If a conflict is detected during probing or operation, the device must stop using the name and try to allocate a new one.
  • Incremental Numbering: To maintain automation, devices typically append a number to their name (e.g., changing from printer.local to printer-2.local) to resolve the conflict.

Cache Maintenance and Goodbye Packets

To save bandwidth, mDNS relies on TTL (Time To Live) (recommended 120 seconds). When a device shuts down normally, it must send a Goodbye Packet with TTL=0. This tells other devices on the network to immediately flush their cache, preventing users from seeing "zombie" (offline) devices in their apps.

Service Discovery Layer: DNS-SD

mDNS solves "Name to IP," while DNS-SD (DNS-Based Service Discovery) solves "What does this device offer?"

The Three-Layer Architecture of DNS-SD

Imagine looking for a printer. The DNS-SD process looks like this:

  1. Categorical Query (PTR Record):

    • Q: "Who here is a printer?" (Query _ipp._tcp.local)
    • A: "Office_Printer._ipp._tcp.local is a printer."
    • Role: Uses PTR records to get the service's Instance Name.

  2. Locating the Host (SRV Record):

    • Q: "Where is Office_Printer?"
    • A: "It's at printer.local, Port 631."
    • Role: Uses SRV records to get the target hostname and port.

  3. Attribute Details (TXT Record):

    • Q: "What are the specs of this printer?"
    • A: "Model is HP-M15w, supports A4 paper."
    • Role: Uses TXT records to get additional parameters (e.g., path=/admin, model=HP).

💡 Technical Tip: Even if a device offers multiple services (like Web UI + Data Stream), use the same Instance Name so users intuitively link different services to the same physical device.

Service Naming and Identification

Use the standard format so other devices understand your service:

  • Service Type: _<Service>._<Proto>
    • Examples: _http._tcp (Web), _ipp._tcp (Printer).
    • Custom: It's recommended to use _custom._udp.
  • Instance Name: <Instance>.<Service Type>.local
    • Example: SmartLight._http._tcp.local.

Practical Guide and Debugging

Here is a practical example (ESP-IDF plus Node.js) that makes an embedded device automatically discoverable by a backend server, so the client no longer needs a hardcoded IP.

ESP32 Firmware (Server)

On ESP-IDF I use the official espressif/mdns component to implement the mDNS Responder.

Step 1: Add Dependency (idf_component.yml) Include the mDNS component in your project configuration:

Step 2: Initialize and Announce Service

After connecting to Wi-Fi, run the following code to start the service:

  1. Init mDNS: Start the background task.
  2. Set Hostname: Sets the device address on the LAN (mydevice.local).
  3. Register Service: Announce service type _wells._udp and listening Port (9001).

// main/udp_stream.c
static void start_mdns_service(void)
{
    // 1. Initialize mDNS service
    ESP_ERROR_CHECK(mdns_init());

    // 2. Set Hostname -> mydevice.local
    mdns_hostname_set("mydevice");
    mdns_instance_name_set("mydevice wells");

    // 3. Register Service: _wells._udp, on Port 9001
    // Clients can find this device by searching for "_wells._udp"
    mdns_service_add("mydevice", "_wells", "_udp", 9001, NULL, 0);
    
    ESP_LOGI(TAG, "mDNS service started: mydevice.local");
}

Node.js Client

On the client side, rely on the OS's native mDNS resolution (Node.js dns module) rather than heavy third-party NPM packages.

This approach is lightweight. It avoids pulling a complex mDNS implementation into Node.js and leans on the OS's underlying resolver instead. If your computer can ping mydevice.local, the code will work.

Core Logic:

  1. Remove Hardcoded IP: Stop using 192.168.0.x.
  2. OS-Level Resolution: Use dns.lookup('mydevice.local') to let the OS (Windows 10+/macOS/Linux Avahi) find the device.
  3. Health Check Loop: Implement a "Fast Discovery" and "Slow Monitoring" loop to auto-update when the IP changes.

// backend/server.js
const dns = require('dns');
const HOSTNAME = 'mydevice.local'; // Target Hostname

function resolveDevice() {
  // Call OS to resolve .local domain (Uses mDNS under the hood)
  dns.lookup(HOSTNAME, { family: 4 }, (err, address) => {
    if (err) {
      console.log(`[mDNS] Searching for ${HOSTNAME}...`);
      return; // Device offline or resolution failed
    }
    
    // Resolved successfully. Update connection if IP changed.
    if (CONFIG.ESP32_IP !== address) {
      console.log(`[mDNS] Discovered: ${address}`);
      CONFIG.ESP32_IP = address;
      
      sendHandshake();      // Send handshake immediately
      startHealthPolling(); // Switch to slow monitoring (check every 10s)
    }
  });
}

The Pitfall of Windows Firewall and NPM Packages

In the Node.js ecosystem, many developers instinctively grab a pure JavaScript implementation like bonjour:

1
2
3
4
5

const bonjour = require('bonjour')()

bonjour.find({ type: 'http' }, function (service) {
  console.log('Found an HTTP server:', service)
})

But often no devices turn up no matter how long you search. The reason is that these packages open their own UDP Socket (Port 5353). On Windows, Windows Defender Firewall blocks incoming UDP packets for unauthorized apps by default. This means your query goes out, but the response is blocked.

Unless users manually allow Node.js in the firewall, these pure JS implementations often fail on Windows.

This is why I recommend dns.lookup(): Since the OS (Windows 10+) already has a built-in mDNS Client with proper firewall rules, using the OS API is much more reliable.

Conclusion

With all of that wired up, the ESP32 is discovered automatically on the local network and there's no hardcoded IP left to maintain.

mDNS gets much less useful across subnets (VLANs), where multicast packets usually don't cross routers and you need something like an mDNS Reflector to bridge them, which is beyond this guide's scope. For most smart home or local network development, what's here covers it.
