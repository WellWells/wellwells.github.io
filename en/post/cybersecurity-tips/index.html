Cybersecurity Risks & Prevention: Wi-Fi to Website Security

From weak Wi-Fi passwords, domain scripts and WinPE login bypass to unencrypted Cookies and broken API checks: real cases of common attacks in Taiwan and how to defend against them.

Introduction

Cybersecurity is a concern neither enterprises nor individuals can dodge, but in Taiwan many companies, institutions, and even personal users still skip the basics, which makes it easy for hackers to break into systems, steal confidential information, and even bring operations to a halt.

Most cybersecurity holes don't need advanced hacking skills; they usually come down to a lack of basic security awareness, which is all an attacker needs to get through. This article walks through some of the most common attack methods in Taiwan, including weak password exploitation, Cookie-based privilege escalation, and website API vulnerabilities.

These techniques look simple, but weak awareness and thin protection are exactly what turns them into serious breaches. Everything below comes from real cases and observations.

Wi-Fi Password Security Risks

In Taiwan, many enterprises and public venues use overly simple and easily predictable Wi-Fi passwords, allowing hackers to infiltrate internal networks without requiring brute-force attacks or advanced hacking techniques.

Key Risk Factors:

  1. Predictable passwords (e.g., 12345678, 88888888).
  2. Company or landline phone numbers.
  3. Unified business number. (8 digits)
  4. Personal mobile phone numbers.

Weak passwords fall quickly to dictionary attacks, and public company details or personal phone numbers can be pieced together through open-source intelligence (OSINT) or social engineering. So it's better to add special characters or switch to longer, readable passphrases.

For example, a company Wi-Fi password can be set as:

1

Thisispasswordforacompany2025$

Alternatively, for home networks, a password can be set using mobile number + special character + word:

1

0910000123@home

Longer, readable passphrases clearly cut the risk of being cracked and are far safer than purely numeric passwords.

A fully random password (e.g., ^Wa091UW!N@U123QQ-USA) is the most secure, but the average user finds it hard to type and remember, so in practice it ends up less usable.

Vulnerabilities in Domain Management Automation Scripts

IT administrators (MIS engineers) usually rely on domain management to centrally manage user workstations, set access permissions, and monitor user activity in real time, including login IP addresses, connection status, and access logs.

These automation scripts often live on specific domain URLs. Using Autoruns to inspect the startup scripts a system runs at boot reveals the corresponding server paths.

A major flaw shows up when the system stores the Administrator account password in plaintext on the server, with no proper encryption or access control.

1
2

net user Administrator /active:yes
net user Administrator XXXXXXXXX

Once an attacker has this file, they can read the highest-privilege user's password on the local machine and raise their own access all the way up.

To simplify management, some admins package privileged installation files separately so standard users can install the software themselves.

These packaged executables can use the Win32 API to escalate privileges, or wrap a password-change script inside an executable. On run, the script is unpacked to a set system directory, executed, then deleted automatically. If this mechanism isn't controlled properly, it leaves a security risk behind.

Unpacking the executable exposes the password-change script. The stored password is usually recorded in ASCII format, which decodes straight back to plaintext.

Bypassing Login Restrictions and Gaining Elevated Privileges Using WinPE

To gain full administrative privileges or access to hard disk files, if BitLocker is not enabled on Windows, tools like WinPE (such as USBOX 7.0) can be used to bypass login restrictions and directly modify or extract relevant files.

Once accessing the system through WinPE, open the Command Prompt, back up the Magnify.exe file, and then replace it with the Command Prompt (cmd.exe).

1
2
3

cd C:\windows\system32
ren Magnify.exe Magnify.back
copy cmd.exe Magnify.exe

Restart the computer and access the Windows login screen. Click on Ease of Access in the lower-right corner, select and launch Magnifier. At this point, the system will open cmd.exe and execute it with SYSTEM privileges.

Next, execute the following command to enable the local Administrator account and set the password to MY_NEW_PASSWORD:

1
2

net user administrator /active:yes
net user administrator MY_NEW_PASSWORD

Once successful, restore the system files:

1
2
3

cd C:\windows\system32
del Magnify.exe
ren Magnify.back Magnify.exe

Restart the computer and log in as Administrator to perform the desired tasks.

Before rebooting, check whether the system has written any related scripts. Some of them clear every user under the Administrator account on login, so it's safer to disconnect the network while doing this.

To block this WinPE route into system files, enable BitLocker encryption so WinPE can't read the disk contents.

Cookie Authentication Vulnerability

Some websites use Cookies to authenticate user login sessions, which can pose a security risk.

As previously mentioned in the article "CVE-2024-9970: Vulnerability Analysis of Privilege Escalation in NewType FlowMaster BPM Plus System", a system used Cookies to authenticate identity, where the user ID was stored in the Cookie in Base64 encoding. Due to the lack of proper verification and preventive measures, an attacker can easily impersonate other users by modifying the ID in the Cookie.

Most implementations follow this process:

  1. User login authentication: The user submits credentials (such as username and password), which the server validates and then generates a unique session token or JWT, potentially containing the user ID and other identity information.
  2. Credential processing and transmission: The server sends the token to the client via Cookie. Modern secure implementations encrypt or digitally sign the Cookie contents to prevent tampering.
  3. Subsequent request validation: The user's browser automatically sends the Cookie in subsequent requests, and the server verifies the legitimacy, integrity, and validity of the token to confirm the user's identity and permissions.
  4. Security attribute configuration: To guard against risks like Cross-Site Scripting (XSS), the HttpOnly and Secure attributes are set on the Cookie so only the server can read it and it travels only over encrypted connections.

The website in question writes the ASP.NET_SessionId Cookie, which the ASP.NET Session system generates and manages automatically. Its own final implementation, though, is what introduces the security flaw.

Cookie Attack Techniques

After a user logs into a website, the server and client authenticate the user through Cookies, which act as a digital identity card. If an attacker steals the Cookie, they can impersonate the user, bypass password verification, and reach protected system resources.

There are several ways an attacker can obtain a user's Cookie, including:

  1. Exporting and importing through browser extensions
  2. Man-in-the-Middle (MiTM) attacks
  3. Cross-Site Scripting (XSS) attacks
  4. Local access or related tools
  5. Others...

Since most websites don't actively check for changes in the user's device or environment, a stolen Cookie is often hard to spot. To cut the risk of Cookie leakage, make sure the device is used only by its owner, which is what keeps unauthorized access out. A further step is antivirus software, which stops malware from tampering with the system's root certificates and intercepting or stealing sensitive data.

Insecure API Authentication Mechanisms Leading to Unauthorized Access and Data Tampering

In API design, some websites trust client-provided credentials too much and skip strict backend verification, which lets attackers bypass authentication and carry out unauthorized access or data tampering, badly compromising system security.

Such API requests can be intercepted and modified with tools like Fiddler AutoResponder or the browser's built-in Developer Tools, which let an attacker overwrite requests or responses locally to sway how the server handles them.

A few measures for API security:

  • Backend validation: Every request should be fully validated by the server, never trusted on client-provided credentials alone.
  • Request signing: Use HMAC, JWT, or other cryptographic mechanisms to protect the integrity and authenticity of API requests against tampering.
  • Response integrity validation: Run integrity checks on response data so an attacker can't intercept and rewrite the response to fool the system.

Below are three possible API security flaw cases for reference:

API Authentication Vulnerability Leading to Unauthorized Privilege Escalation

A website's login relies on a backend API for identity verification and enables specific features based on what it returns. The catch is that what the page shows depends entirely on the API response, so an attacker who intercepts and rewrites that response can pick up unauthorized administrator privileges, leading to privilege escalation or data leakage.

Missing API Parameter Validation Leading to Price Tampering Vulnerability

In an online ordering platform, when users add items to their cart, the frontend sends an API request carrying price, product ID, and other fields. This API runs no server-side validation on the price parameter and doesn't encrypt the request either, so an attacker who intercepts the request can change the product price by hand, close the transaction below the real price, and cause revenue loss.

Insufficient Email API Field Validation Leading to Sender Forgery Vulnerability

A website's "Export Report" feature lets users send reports via API to a chosen email address. In the original design, the API's default sender is admin@google.com, while the recipient is set by the user. But the API lets clients submit the sender and recipient addresses directly, and the backend never locks the sender field, so an attacker can forge the sender identity and impersonate any address to send malicious emails.

These cases all show how badly a weak API authentication mechanism can hurt. When designing an API, enterprises should at least cover:

  • Solid authentication to prevent credential tampering and identity spoofing.
  • Integrity protection for requests and responses to guard against malicious data tampering.
  • Critical parameters not directly controlled by the client, to shrink the business risk and the attack surface.

Conclusion

Hacking techniques keep evolving, yet many enterprises and individuals still skip basic cybersecurity, which leaves their systems open. Weak passwords, domain management holes, Cookie-based privilege escalation, and API validation flaws all come down to the same thing: thin security awareness and incomplete protection.

A few places to start:

  1. Strengthen authentication: Use strong passwords and turn on two-factor authentication (2FA) to keep accounts from being taken over.
  2. Lock down domain and permissions: Encrypt management scripts, limit high-privilege account access, and block unauthorized actions.
  3. Manage Cookies and sessions: Set HttpOnly, Secure flags, add a Session Timeout, and cut the risk of credential theft.
  4. Never trust client-provided data: Every client-side input (API requests, Cookies, URL parameters, form data, etc.) should be validated and filtered server-side against SQL injection, XSS, privilege escalation, and the rest.
  5. Pick safer system solutions: Stay away from low-cost, unsupported systems, and run security tests regularly.
  6. Enable BitLocker encryption: Keep disk data from being stolen through WinPE or physical access.

Cybersecurity is something you keep up over time. Testing for holes and watching for odd behavior regularly is a lot less work than patching things up after a breach.
