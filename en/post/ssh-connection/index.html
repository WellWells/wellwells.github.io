Using SSH Keys for Password-Free Remote Connections

SSH keys let you log in remotely without a password: generating the key pair, filling in authorized_keys, writing config, then disabling password auth, caching the passphrase with ssh-agent, and agent forwarding.

Introduction

Secure Shell (SSH) is a secure protocol that allows two computers to exchange data (execute commands, transfer files) over an encrypted connection, which keeps the data safe and intact.

SSH is commonly used for remote login between two computers. It replaces older remote access protocols, such as Telnet, which transmitted passwords and data in plain text without encryption. In 2020, PTT also discontinued the insecure Telnet protocol, switching to SSH or WebSocket so that all communication is encrypted and cannot be eavesdropped on or tampered with.

Besides remote connections, SSH can also:

  • Establish SSH tunnels for port forwarding, securely accessing network resources.
  • Use SFTP and SCP for secure file transfers.
  • Use rsync for file synchronization, reducing transfer volumes.
  • And more...

By default, Linux, macOS, and Windows integrate the OpenSSH package. OpenSSH is an open-source implementation of SSH, and it includes:

  • Remote operation tools:

    • ssh, for remote login to other hosts and command execution.
    • scp, for file transfer between local and remote hosts.
    • sftp, similar to FTP but with encrypted transfers.

  • Key management tools:

    • ssh-add, adds private keys to the SSH agent, allowing password-free authentication using private keys.
    • ssh-keysign, for signing SSH certificates for authentication.
    • ssh-keyscan, for retrieving SSH public keys from remote hosts.
    • ssh-keygen, for generating SSH key pairs (public and private keys).

  • Server-side components:

    • sshd (SSH Daemon), a daemon running on the server, responsible for accepting SSH connection requests from clients.
    • sftp-server, handles requests from sftp clients for file transfers.
    • ssh-agent, manages the user's SSH keys and hands them over for authentication when needed.

This article will focus on how to create public and private keys and use them to achieve password-free authentication. It will also cover how to run SSH services on the server side and allow the client to connect via SSH.

Traditionally, password login involves entering the correct user password for authentication. If the server is exposed to the public network, it may face brute force attacks, leading to data leakage.

To improve security (and avoid typing passwords?), you can authenticate with a public and private key pair instead. This way, you don't need to enter a password to connect, and hackers cannot log in without the private key.

💡 This article uses Tailscale to establish a local network, enabling connections between the local and server computers via hostname or IP address.

Both computers need an IP address to connect. If it's a public IP address, you need to set up port forwarding on the router to the local network, which exposes the SSH port to danger. If you don't want to expose the port, don't have a public IP address, or can't modify router settings, you can read Using Tailscale to Easily Create Secure and Private Tunnels to achieve connections between two computers.

SSH Key Points Summary

  1. SSH mainly supports two authentication methods:

    • Password-based authentication
    • Public-key authentication

  2. Once SSH keys are set up, you can use key-based login without needing to enter a password.

  3. Public key content will be placed in authorized_keys on the remote server.

  4. Private key will be kept on your local system. Protect this private key and do not share it.

  5. The public key can be shared with anyone, but only you should have access to the private key.

  6. SSH can use different encryption algorithms. RSA is the default, widely used, and most compatible method; Ed25519 offers better performance but less compatibility compared to RSA, and most servers are gradually adding support for it, which makes it my preferred choice for generating keys. Either way, all that matters is that the local machine and the server can talk to each other.

  7. Most Git transmission protocols use SSH. This means remote operations like clone, push, pull will require authentication.

Although RSA is more compatible than Ed25519, it is recommended to generate Ed25519 keys for better security and speed.

SSH Key Creation and Connection Process

Assuming nodeA is the local client (user) and nodeB is the server.

NodeA is the working computer, used for tasks like git clone or SSH connections to other computers.

NodeB is the connected computer, such as a git server, web server, proxy server, or VPS...

  1. Generate keys (public and private) on either nodeA or nodeB.
  2. Place the private key on nodeA and the public key on nodeB.
  3. On nodeB, create ~/.ssh/authorized_keys and add the public key.
  4. On nodeA, create ~/.ssh/config and add connection information, including the server's IP address and private key path.
  5. From then on, nodeA's SSH connections will use the key by default.

💡 Notes:

  1. Make sure the private key is only accessible to you, and that nodeB does not have a copy.
  2. If nodeB is Windows and you're an admin, change the path to: C:\ProgramData\ssh\administrators_authorized_keys
  3. If the connection fails or prompts for a password after setting up keys, add -vvvv to the SSH command for debugging.

Generating SSH Keys

From the previous SSH connection behavior, it is evident that the key pair has not been set up, so the default login is using a password.

Generating SSH keys is simple, and can be done on either the client or the server side.

On both Windows and Linux, you can generate keys using the ssh-keygen command.

Parameters include:

  • -t ed25519 generates an ed25519 key pair. Alternatively, you can use -t rsa -b 4096 to generate an RSA key with a length of 4096 bits.
  • -C "xxx" allows you to add a comment to help identify the key, where xxx is any value you choose.
1

ssh-keygen -t ed25519 -C "your_email@example.com"

During the key generation process, you will see a prompt Enter file in which to save the key. By default, this path is under the .ssh folder in your home directory.

After deciding on the path, you will be prompted for a passphrase (key password). If left empty, you will not need to enter a password when using the key for authentication in the future; if you set one, a hacker who obtains the private key still has an additional layer to bypass.

The key is stored on your personal computer and under your personal account, so the risk of it being leaked is generally low. If you are concerned about the key being leaked, you can enter a non-empty passphrase. This way, even if the private key is compromised, a password is still required for authentication. But that adds an extra step each time you use the key...

The passphrase can be cached using ssh-agent, so you do not need to retype it within the cache time.

Setting a passphrase here is worth the extra security, paired with key passphrase with ssh-agent for caching.

Establishing a Connection Between Two Computers Using SSH Keys

Next, copy the public key (nodeA_ed25519.pub) to the server, which can be done with the scp (secure copy) program.

The usage is: scp local_file_path username@server:server_path

Copying the public key from Windows to Windows

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:C:\Users\wells_nodeB\.ssh\nodeA_ed25519.pub

Copying the public key from Windows to Linux

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:~/.ssh/nodeA_ed25519.pub

After entering the password, scp copies the public key to the server.

1

wells@nodeB's password:
nodeA_ed25519.pub                                                                                  100%  102     1.2KB/s   00:00

After copying, on nodeB (the server), create a new file and add the public key content.

User paths depend on the user on nodeB

  • Windows regular user: C:\Users\wells_nodeA\.ssh\authorized_keys
  • ⚠️ Windows system user: C:\ProgramData\ssh\administrators_authorized_keys
  • Linux regular user/root: ~/.ssh/authorized_keys
  1. Open the public key file (nodeA_ed25519.pub) with a text editor.
  2. Select and copy the entire content.
  3. Create the appropriate file as listed above.
  4. Paste the public key content into the new file and save.

Finally, add and save the config file on the local machine nodeA:

  • Windows: C:\Users\wells_nodeA\.ssh\config
  • Linux: ~/.ssh/config
1
2
3
4

Host nodeB_wells
    User wells
    HostName nodeB
    IdentityFile ~/.ssh/nodeA_ed25519

Configuration file details

  • Host is a user-defined name for easy identification.
  • User is the username on the server.
  • HostName is the server's IP address or hostname.
  • IdentityFile is the path to the private key. You can use ~/ to denote the home directory on both Windows and Linux.

After saving, you should be able to log in using the key. If the login fails and asks for a password, check the following:

  • The key is correct.
  • The authorized_keys path is correct.

Connect over SSH again, and this time it will not prompt for a password.

Accessing a Git Server on Synology Using SSH Keys

After generating the key pair on your local Windows/Linux machine, place the public key in the .ssh directory under your personal user directory on Synology. If the directory does not exist, you will need to create it. Then, create an authorized_keys file and add the public key content to it.

On your local machine, add the host information to the config file:

  • Windows: C:\Users\wells\.ssh\config
  • Linux: ~/.ssh/config
1
2
3
4

Host NAS
    User wells
    HostName 192.168.50.12
    IdentityFile ~/.ssh/nodeA_ed25519

Configuration file details

  • Host is a recognizable name for the server.
  • User is the NAS login username.
  • HostName is the NAS IP address.
  • IdentityFile is the path to the private key.

When executing git remote related commands, the key is used for authentication first, so no password is needed.

Advanced Security Settings

This section is for users who are sensitive to security concerns. The config settings below are worth adding for higher security.

Disable Password Authentication

If the default remote server (nodeB) uses password authentication, you can increase security by disabling it once key-based login works.

Configuration file paths:

  • Windows: C:\ProgramData\ssh\sshd_config
  • Linux: /etc/ssh/sshd_config

Locate the line around line 50 and change PasswordAuthentication to no, and remember to remove the preceding #.

1
2

---#PasswordAuthentication yes
+++PasswordAuthentication no

After making the changes, restart sshd:

1

Restart-Service sshd

Restart sshd on Linux:

1

sudo service ssh restart

Key Passphrase with ssh-agent

In the Generating SSH Keys section, it was mentioned that the passphrase can be left empty by default, so no password is required when using SSH. But if the private key is compromised, a hacker can connect over SSH with it directly.

So add a passphrase when generating the key and use ssh-agent to cache the private key in memory. After entering the passphrase once, key authentication uses that cache.

The following steps use Windows as an example, but the process is generally the same for Linux.

The main difference is that on Windows, the SSH executable is divided into two packages:

  1. OpenSSH located at C:\Windows\System32\OpenSSH
  2. Git located at C:\Program Files\Git\usr\bin

Therefore, you need to change Git's sshCommand to the OpenSSH path.

Windows:

# Change Git's ssh.exe to the path under OpenSSH. If not changed, you won't be able to use the private key stored in OpenSSH's memory.
git config --global core.sshCommand C:/Windows/System32/OpenSSH/ssh.exe

# Automatically Start ssh-agent on Boot
Get-Service ssh-agent | Set-Service -StartupType Automatic

# Start ssh-agent
Start-Service ssh-agent

# Check the status of ssh-agent
Get-Service ssh-agent

# Use ssh-add to add the private key to ssh-agent. You will be prompted to enter the passphrase.
ssh-add C:\Users\wells\.ssh\nodeA_ed25519

# List the keys currently loaded in ssh-agent
ssh-add -l

# Delete all keys
# ssh-add -D

Linux:

1
2
3
4
5

# If the default shell is bash, add the following line at the end of ~/.bashrc
eval "$(ssh-agent -s)"

# Add the private key to ssh-agent and enter the passphrase
ssh-add ~/.ssh/nodeA_ed25519

The commands on macOS might differ slightly. Please refer to the solution for details.

Once ssh-agent has loaded the private key, you can back the key up to a secure location and remove it from this computer.

As long as ssh-agent is running, key authentication will be handled through the agent by default.

Finally, the .ssh folder on the local machine (nodeA) should only contain known_hosts and config.

You can also remove the IdentityFile path from the config file.

1
2
3

Host nodeB_wells
    User wells
    HostName nodeB

By default, ssh-agent keeps the keys loaded indefinitely. For tighter security, you can set a cache timeout period.

1

ssh-agent -t 1h

Using SSH Agent Forwarding

The public key has been added to both GitHub and nodeB, and the private key has been added to ssh-agent on the local machine (nodeA) using ssh-add.

This setup allows the local machine to SSH into nodeB or use git commands to clone repositories from GitHub to nodeA.

Now, if you want to git clone a repository from GitHub on nodeB, you don't need to place the private key on nodeB.

You can use SSH agent forwarding here.

1
2

# Adding the `-A` option enables SSH agent forwarding, allowing the use of local SSH keys on the remote server.
ssh -A wells@nodeB

If you find it cumbersome to add the -A option every time you SSH, you can add ForwardAgent to your config file.

1
2
3
4

Host nodeB_wells
    User wells
    HostName nodeB
    ForwardAgent yes

After connecting, you can use ssh-add -l on the remote server to check if the private key has been loaded.

If the private key is loaded, you can then perform a git clone on nodeB using that key.

The default version on Windows is 8.6p1, and after agent forwarding, the private key appears to be loaded on the server.

But performing a git clone may result in public key authentication failure due to an OpenSSH bug.

Windows users can manually install version 8.9p1 from Microsoft's OpenSSH Release to resolve this issue and perform git operations normally.

Also, if the trust level of nodeB is low (e.g., other users on it have root privileges), consider using ProxyJump for intermediate hopping. The principle is to keep the private key on nodeA and configure nodeA as a jump host when accessing GitHub from nodeB.

The advantage is that it does not forward the private key from nodeA to nodeB, but instead performs SSH operations directly on nodeA and returns the results to nodeB.
