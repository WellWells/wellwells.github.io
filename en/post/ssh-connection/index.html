Using SSH Keys for Password-Free Remote Connections

SSH keys let you log in remotely without a password: generating the key pair, filling in authorized_keys, writing config, then disabling password auth, caching the passphrase with ssh-agent, and agent forwarding.

Introduction

Secure Shell (SSH) is a secure protocol that allows two computers to exchange data (execute commands, transfer files) over an encrypted connection, which keeps the data safe and intact.

SSH is commonly used for remote login between two computers. It replaces older remote access protocols, such as Telnet, which transmitted passwords and data in plain text without encryption. In 2022, PTT also discontinued the insecure Telnet protocol, switching to SSH or WebSocket so that all communication is encrypted and cannot be eavesdropped on or tampered with.

Besides remote connections, SSH can also:

  • Establish SSH tunnels for port forwarding, securely accessing network resources.
  • Use SFTP and SCP for secure file transfers.
  • Use rsync for file synchronization, reducing transfer volumes.

By default, Linux, macOS, and Windows integrate the OpenSSH package. OpenSSH is an open-source implementation of SSH. This article uses the following tools:

  • ssh, for remote login to other hosts and command execution.
  • scp, for file transfer between local and remote hosts.
  • ssh-keygen, for generating SSH key pairs (public and private keys).
  • ssh-add, adds private keys to ssh-agent.
  • ssh-agent, holds the user's SSH keys on the client and hands them over for authentication when needed.
  • sshd (SSH Daemon), a daemon running on the server, responsible for accepting SSH connection requests from clients.

This article focuses on creating public and private keys and using them for password-free authentication. It also covers running the SSH service on the server so clients can connect.

Traditionally, password login involves entering the correct user password for authentication. If the server is exposed to the public network, it may face brute force attacks, leading to data leakage.

To improve security (and avoid typing passwords?), you can authenticate with a public and private key pair instead. This way, you don't need to enter a password to connect, and hackers cannot log in without the private key.

💡 This article uses Tailscale to establish a local network, enabling connections between the local and server computers via hostname or IP address.

Both computers need an IP address to connect. If it's a public IP address, you need to set up port forwarding on the router to the local network, which exposes the SSH port to danger. If you don't want to expose the port, don't have a public IP address, or can't modify router settings, you can read Using Tailscale to Easily Create Secure and Private Tunnels to achieve connections between two computers.

SSH Key Creation and Connection Process

nodeA is the local client, the computer you work on. nodeB is the server you connect to, such as a git server, web server, or VPS.

  1. Generate keys (public and private) on either nodeA or nodeB.
  2. Place the private key on nodeA and the public key on nodeB. The public key can be shared. Only you should have access to the private key, and nodeB should not keep a copy.
  3. On nodeB, create ~/.ssh/authorized_keys and add the public key.
  4. On nodeA, create ~/.ssh/config and add connection information, including the server's IP address and private key path.
  5. From then on, nodeA uses the key when you connect with the Host name from the config.

💡 Notes:

  1. If nodeB is Windows and your account belongs to the Administrators group, change the path to: C:\ProgramData\ssh\administrators_authorized_keys
  2. If the connection fails or still prompts for a password after setting up keys, see Connection Troubleshooting.

Generating SSH Keys

You can generate keys on either the client or the server. On both Windows and Linux, the command is ssh-keygen:

1

ssh-keygen -t ed25519 -C "your_email@example.com"
  • -t ed25519 generates an Ed25519 key pair. Since OpenSSH 9.5 (2023), ssh-keygen generates Ed25519 keys by default. Ed25519 keys are short and faster than RSA, and nearly all servers support them, which makes Ed25519 my preferred choice. RSA has the widest compatibility and is only needed for older devices that do not support Ed25519. Use -t rsa -b 4096 for a 4096-bit RSA key.
  • -C "xxx" adds a comment of your choice to help identify the key.

During generation you will see the prompt Enter file in which to save the key. The default path is the .ssh folder in your home directory.

You will then be asked for a passphrase (key password). I recommend setting one, because a hacker who obtains the private key still has to get past it. If left empty, no password is needed when using the key, but a leaked private key can be used to connect directly. A passphrase can be cached with key passphrase with ssh-agent, so you do not have to type it each time.

Establishing a Connection Between Two Computers Using SSH Keys

The next step is adding the public key to authorized_keys on nodeB. This step still uses a password to log in to nodeB, so complete it before disabling password authentication.

One-Line Public Key Install (nodeB Is Linux)

When nodeA is Linux or macOS, use ssh-copy-id:

1

ssh-copy-id -i ~/.ssh/nodeA_ed25519.pub wells@nodeB

Windows does not include ssh-copy-id. In PowerShell, the following command does the same job:

1

Get-Content ~/.ssh/nodeA_ed25519.pub | ssh wells@nodeB "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Enter the nodeB password once and the install is complete. This command creates ~/.ssh on nodeB, appends the public key to authorized_keys, and sets the permissions. The chmod calls are required: sshd checks permissions by default and ignores the key if other users can write to these paths, which falls back to password login.

Running this line twice adds a duplicate public key line to authorized_keys, which does not affect login. ssh-copy-id skips keys that already exist.

After installing the key, continue to setting up the config.

Manual Public Key Install (nodeB Is Windows)

The Windows sshd uses cmd.exe by default, so the mkdir -p and chmod calls above cannot run and the key has to be installed manually. These steps also work for Linux users who want to perform each step themselves.

First create the .ssh folder in your home directory on nodeB. Otherwise scp fails because the path does not exist. Then use scp (secure copy) to copy the public key (nodeA_ed25519.pub) to the server.

The usage is: scp local_file_path username@server:server_path

Copying the public key from Windows to Windows

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:C:\Users\wells_nodeB\.ssh\nodeA_ed25519.pub

Copying the public key from Windows to Linux

1

scp C:\Users\wells_nodeA\.ssh\nodeA_ed25519.pub wells@nodeB:~/.ssh/nodeA_ed25519.pub

After entering the password, scp copies the public key to the server.

After copying, on nodeB (the server), create a new file and add the public key content.

The path depends on the login account on nodeB

  • Windows regular user: C:\Users\wells_nodeB\.ssh\authorized_keys
  • ⚠️ Windows Administrators group member: C:\ProgramData\ssh\administrators_authorized_keys
  • Linux regular user/root: ~/.ssh/authorized_keys
  1. Open the public key file (nodeA_ed25519.pub) with a text editor.
  2. Select and copy the entire content.
  3. Create the appropriate file as listed above.
  4. Paste the public key content into the new file and save.

Next, set the permissions on nodeB. On Linux:

1
2

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

On Windows, administrators_authorized_keys must be accessible only to Administrators and SYSTEM. Open PowerShell as an administrator and run:

1

icacls.exe "$env:ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"

Set Up the Config and Connect

Add and save the config file on the local machine nodeA:

  • Windows: C:\Users\wells_nodeA\.ssh\config
  • Linux: ~/.ssh/config
1
2
3
4
5

Host nodeB_wells
    User wells
    HostName nodeB
    IdentityFile ~/.ssh/nodeA_ed25519
    IdentitiesOnly yes

Configuration file details

  • Host is a user-defined name for easy identification.
  • User is the username on the server.
  • HostName is the server's IP address or hostname.
  • IdentityFile is the path to the private key. You can use ~/ to denote the home directory on both Windows and Linux.
  • IdentitiesOnly limits SSH to the key named in IdentityFile. Otherwise other keys in ssh-agent may be tried first, and enough failed attempts end in Too many authentication failures.

After saving, connect with the Host name from the config, and this time it will not prompt for a password.

1
2
3
4
5
6
7
8
9

C:\Users\wells_nodeA>ssh nodeB_wells

Microsoft Windows [版本 10.0.22631.2861]
(c) Microsoft Corporation. 著作權所有，並保留一切權利。

wells@NODEB C:\Users\wells>exit
Connection to nodeB closed.

C:\Users\wells_nodeA>

The connection must use nodeB_wells. ssh wells@nodeB does not match Host nodeB_wells, so that block is not applied and nodeA_ed25519 is not used.

Connection Troubleshooting

If the remote connection fails, add -vvv to the connection attempt, for example:

1
2
3
4
5
6
7

C:\Users\wells_nodeA>ssh -vvv wells@nodeB

OpenSSH_for_Windows_8.6p1, LibreSSL 3.4.3
...
debug1: Connecting to server [100.100.120.16] port 22.
debug1: connect to address 100.100.120.16 port 22: Connection timed out
ssh: connect to host server port 22: Connection timed out

Connection timed out means no response came back. Possible reasons include:

  • The server's firewall is blocking the connection (computer, antivirus software, router).
  • Port 22 is blocked on the client side.
  • The IP address is wrong or the server is powered off.

Other common error messages:

  • Connection refused: the server responded, but no service is listening on port 22. sshd is usually not running.
  • Could not resolve hostname: DNS resolution failed. Check that the hostname is correct.

If the login fails or still asks for a password, check the following:

  • The key is correct.
  • The authorized_keys path is correct.
  • On Linux, ~/.ssh is 700, authorized_keys is 600, and only you can write to your home directory.
  • On Windows, the permissions on administrators_authorized_keys are set.
  • The connection uses the Host name from the config.

Accessing GitHub Using SSH Keys

First, create a new repository on GitHub. If you already have one, skip this step.

After creating the repository, GitHub gives you an SSH link.

1

git@github.com:WellWells/TEST_REPO.git

If you attempt to clone the repository directly on your local machine, you will encounter a permission error:

1
2
3
4
5
6
7

wells@server:~$ git clone git@github.com:WellWells/TEST_REPO.git
Cloning into 'TEST_REPO'...
git@github.com: Permission denied (publickey).
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.

Click on the personal icon in the top right corner to open the menu, then select "Settings" to go to the settings page.

On the left, select "SSH and GPG keys" to enter the SSH Key page, then click "New SSH key" to add your public key.

Add the following to the config on your local machine. Host is set to github.com, so this block applies when connecting to GitHub:

1
2

Host github.com
    IdentityFile ~/.ssh/nodeA_ed25519

Now, when you clone the repository again, you should be able to access the GitHub repo using the SSH key without any issues.

1
2
3

wells@server:~$ git clone git@github.com:WellWells/TEST_REPO.git
Cloning into 'TEST_REPO'...
warning: You appear to have cloned an empty repository.

Advanced Security Settings

Disable Password Authentication

Once key-based login works, you can increase security by disabling password authentication on nodeB.

Configuration file paths:

  • Windows: C:\ProgramData\ssh\sshd_config
  • Linux: /etc/ssh/sshd_config

Locate the line around line 50 and change PasswordAuthentication to no, and remember to remove the preceding #.

1
2

-#PasswordAuthentication yes
+PasswordAuthentication no

After making the changes, restart sshd. From the next login on, only keys work, and a lost key means no access. Before restarting, confirm that key login works and keep one logged-in session open so you can revert a bad setting.

Restart sshd in PowerShell:

1

Restart-Service sshd

Restart sshd on Linux:

1

sudo service ssh restart

On Ubuntu, also verify the effective value. sshd uses the first value it reads, and the top of sshd_config loads the files in /etc/ssh/sshd_config.d/ first. If 50-cloud-init.conf contains PasswordAuthentication yes, the change above has no effect, and that file must be changed too.

1
2
3
4
5

# Show the value sshd actually uses
sudo sshd -T | grep -i passwordauthentication

# Find the file that overrides the setting
sudo grep -r PasswordAuthentication /etc/ssh/sshd_config.d/

Key Passphrase with ssh-agent

ssh-agent holds the decrypted private key. After you enter the passphrase once, ssh-agent performs key authentication.

On Windows, the SSH executables come in two packages:

  1. OpenSSH located at C:\Windows\System32\OpenSSH
  2. Git located at C:\Program Files\Git\usr\bin

So on Windows, change Git's sshCommand to the OpenSSH path.

Windows:

 1

# Change Git's ssh.exe to the path under OpenSSH. If not changed, you won't be able to use the private key held by the Windows ssh-agent.
git config --global core.sshCommand C:/Windows/System32/OpenSSH/ssh.exe

# Automatically Start ssh-agent on Boot
Get-Service ssh-agent | Set-Service -StartupType Automatic

# Start ssh-agent
Start-Service ssh-agent

# Check the status of ssh-agent
Get-Service ssh-agent

# Use ssh-add to add the private key to ssh-agent. You will be prompted to enter the passphrase.
ssh-add C:\Users\wells\.ssh\nodeA_ed25519

# List the keys currently loaded in ssh-agent
ssh-add -l

# Delete all keys
# ssh-add -D

Linux:

1
2
3
4
5
6
7
8

# If the default shell is bash, add the following to the end of ~/.bashrc on nodeA
# Starts an agent only when none is reachable, and all shells share one socket
export SSH_AUTH_SOCK="$HOME/.ssh/agent.sock"
ssh-add -l > /dev/null 2>&1
if [ $? -eq 2 ]; then
    rm -f "$SSH_AUTH_SOCK"
    eval "$(ssh-agent -s -a "$SSH_AUTH_SOCK")" > /dev/null
fi

1
2

# Add the private key to ssh-agent and enter the passphrase
ssh-add ~/.ssh/nodeA_ed25519

The commands on macOS might differ slightly. Please refer to the solution for details.

The Windows ssh-agent is a system service. It encrypts the private key with the current Windows account and stores it in the Registry, so the key stays available after a reboot without the passphrase. Once ssh-agent has loaded the private key, Microsoft recommends backing the key up to a secure location and removing it from this computer.

As long as ssh-agent is running, key authentication will be handled through the agent by default.

Finally, the .ssh folder on the Windows machine (nodeA) should only contain known_hosts and config.

Remove IdentityFile and IdentitiesOnly from the config file together. With IdentitiesOnly alone, SSH does not use the keys in the agent.

1
2
3

Host nodeB_wells
    User wells
    HostName nodeB

The Linux ssh-agent keeps the private key only in memory, so ssh-add has to run again after a reboot. Keep the private key file and IdentityFile on Linux.

By default, ssh-agent keeps the keys loaded indefinitely. For tighter security on Linux, set a lifetime when adding the key:

1

ssh-add -t 1h ~/.ssh/nodeA_ed25519

The Windows ssh-agent does not support lifetimes and rejects -t. Use ssh-add -D to delete keys when you no longer need them.

Using SSH Agent Forwarding

To run git clone on nodeB for a GitHub repository, you can use SSH agent forwarding instead of placing the private key on nodeB. This requires the public key on both GitHub and nodeB, and the private key added to ssh-agent on nodeA with ssh-add.

1
2

# Adding the `-A` option enables SSH agent forwarding, allowing the use of local SSH keys on the remote server.
ssh -A nodeB_wells

You can also add ForwardAgent to the config instead of passing -A each time:

1
2
3
4

Host nodeB_wells
    User wells
    HostName nodeB
    ForwardAgent yes

After connecting, run ssh-add -l on nodeB to list the forwarded keys. The private key itself is not copied to nodeB. If the key is listed, you can run git clone on nodeB.

In 2023, when I used agent forwarding with the 8.6p1 version built into Windows, git clone failed with a public key authentication error. Manually installing 8.9p1 resolved it.

If the trust level of nodeB is low (e.g., other users on it have root privileges), avoid agent forwarding. While you are connected, root on nodeB can use the forwarded agent to authenticate to other hosts.

If you only need to reach a third host through nodeB, use ProxyJump with nodeB as the jump host. The private key stays on nodeA, nodeA authenticates directly with the target host, and nodeB only relays encrypted traffic.

1

ssh -J nodeB_wells wells@nodeC

ProxyJump cannot give programs on nodeB access to the key. If nodeB itself must access GitHub, use a deploy key bound to a single repository instead.

Accessing a Git Server on Synology Using SSH Keys

Place the public key in the .ssh directory under your personal user directory on Synology, creating the directory if it does not exist. Then create an authorized_keys file and add the public key content to it.

Add the NAS to the config on your local machine. User is the NAS login username and HostName is the NAS IP address:

1
2
3
4

Host NAS
    User wells
    HostName 192.168.50.12
    IdentityFile ~/.ssh/nodeA_ed25519

The git remote URL must use the Host name (for example NAS:/volume1/git/project.git). This applies the block above and uses the key, so no password is needed.

If it still asks for a password, first confirm that the user home service is enabled in DSM, then check the permissions. sshd rejects a home directory that the group or other users can write to. Log in to the NAS over SSH with your password and run:

1
2
3

chmod 755 ~
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
