Introduction

When starting a new project, many developers hit the same wall: decision paralysis during tech stack selection.

You've already defined your requirements and core features. You've opened your IDE, ready to code. But then comes an avalanche of questions: Which framework should I use? Which database? How do I integrate the frontend and backend?

So you start digging through Stack Overflow, GitHub Discussions, and Reddit. Framework A advocates praise its mature ecosystem and high productivity. Critics point to bloated bundle sizes and performance concerns. Framework B has polished documentation, but after adopting it, you discover weak community support and outdated examples.

Hours later, your browser is buried under dozens of tabs. Your notes are filled with framework comparisons. Yet you haven't written a single line of actual business logic.

This is the core problem with traditional development. In an age of information overload, the cost of technical decisions goes up while real development work stalls indefinitely.

Below are three tech selection cases I've personally experienced. These decisions seemed reasonable at the time but turned out to be wrong once I started implementing. The root cause was often relying too heavily on fragmented search engine results without a holistic assessment of long-term technical challenges.

The GUI Framework Dilemma

Take desktop application development, for example. Choosing just the graphical user interface (GUI) framework is already a puzzle:

"Should I go with C# WPF or Python GUI?" Or perhaps a frontend-backend hybrid like Electron or Tauri?

If your project has cross-platform requirements—supporting Windows, macOS, and Linux simultaneously—the choice becomes even more complex. Here's a quick overview of the mainstream options:

TechnologyDescriptionCross-PlatformBest For
C# WPF/WinFormsMicrosoft's .NET desktop framework with deep integration and a mature ecosystem❌ Windows onlyEnterprise apps designed specifically for Windows
Python GUI (Tkinter/PyQt)GUI solutions within the Python ecosystem, low barrier to entry✅ SupportedRapid prototyping, data analysis tools, lightweight apps
ElectronBuilt on Chromium and Node.js, uses HTML/CSS/JavaScript for desktop apps✅ SupportedApps needing rich web technologies and npm ecosystem (e.g., VS Code, Slack)
TauriLightweight Rust-based alternative with smaller bundles and better performance✅ SupportedModern apps prioritizing minimal install size and peak performance

Each option has trade-offs. Electron has a mature ecosystem but produces massive bundles (250–500 MB). Tauri is lightweight and performant but requires a Rust environment. C# WPF is full-featured but Windows-only. Python GUI is quick to develop but typically looks dated.

The Database Trap: Full-Text Search Requirements

Another common pain point is database selection, especially when your project needs full-text search (FTS):

"Should I choose MongoDB, Elasticsearch, or PostgreSQL?"

Facing unfamiliar territory, our first instinct is to search online. Someone says NoSQL is great—"No SQL syntax needed, flexible schemas"—so you dive headfirst into MongoDB.

But when your project requires Chinese text search, problems emerge. MongoDB's native Chinese tokenization support is practically nonexistent. Its full-text indexing is designed around English space-delimited words, and it simply can't handle languages like Chinese that lack word separators.

What is tokenization? The core of full-text search lies in "tokenization." For example, "臺北市政府" (Taipei City Government) would be split into tokens like "臺北," "市," and "政府" to build a searchable index. English words are naturally separated by spaces, but Chinese, Japanese, and other languages have continuous text that requires a tokenizer to segment.

When searching for solutions online, you're typically led to two paths:

  1. MongoDB's paid cloud service, Atlas Search. No explanation needed: just pay up.
  2. Self-host a MEK Stack (MongoDB + Elasticsearch + Kafka). You'd use Docker to run three separate services. Data goes into MongoDB, Kafka syncs it to Elasticsearch, and Elasticsearch handles the actual search. It looks professional on paper, but for individual developers, the maintenance overhead is extreme. Your project might never launch because you're too busy wrestling with distributed systems ops.

In contrast, PostgreSQL is the fastest and most efficient solution for individual developers.

It has built-in full-text search. Add zhparser for Chinese tokenization. No extra services to maintain. You get data storage and search capabilities in a single database.

The JavaScript Runtime Dilemma

Beyond database selection, choosing a JavaScript runtime is another challenge.

The mainstream options include Node.js, Deno, and Bun.

Deno does have a few features worth a look:

  • Security Sandbox: Permissions are locked down by default. You must explicitly grant access to the filesystem, network, or environment variables, so you get better runtime security.
  • npm Compatibility: Since Deno 1.28, you can directly import npm packages without being limited to Deno's module system.
  • Zero Config Philosophy: Built-in TypeScript, linter, formatter, and testing tools. Start developing immediately without tedious environment setup.

These features are attractive if you want a modern developer experience.

However, in practice, Deno struggles to integrate with established ecosystems:

  • Can't integrate with Electron: Electron is deeply tied to Node.js architecture. Swapping in Deno is nearly impossible, and the developer experience suffers.
  • Limited mainstream framework support: Next.js and similar widely-adopted frameworks still have integration issues with Deno. While Deno officially recommends Fresh as its native-optimized framework, its community size and ecosystem resources pale in comparison to Next.js.
  • Weak community support: Without an active community and enough third-party packages, developers struggle to build mature, production-ready applications quickly.

Late last year, I tried developing with Deno. I dove in with high expectations, only to encounter a wall of compatibility issues, problems that simply don't exist in Node.js. The Electron + Deno combo was miserable. Switching to Tauri meant wrestling with Rust environment setup first.

These are not really Deno's fault. The community just hasn't grown to that size yet.

While Node.js didn't natively support TypeScript initially (recent versions have begun integrating it), this was never really a problem. Mainstream build tools like Vite and Webpack have had TypeScript compilation integrated for years. Developers barely notice. Node.js with its mature toolchain ecosystem still far exceeds these newer alternatives in stability and compatibility.

So picking the right tool matters.

Yet before we even start writing core business logic, we've already burned massive amounts of time browsing documentation, studying SDK references, and exploring framework boilerplates. Our energy gets drained by configuration and learning curves. This is the reality for most developers.

Agentic Workflow: Plan First, Build Second

From Tech Selection Anxiety to Strategic Dialogue

The challenges above—GUI framework dilemmas, database traps, and then a runtime that won't play with the tools everyone already uses—all point to the same thing. We get trapped in technical details too early, without enough information.

The traditional development path looks like this: see requirements → search online → get lured by framework marketing → make a gut decision → start coding → discover problems → start over. This "learn by failing" approach wastes time and energy. Worse, wrong tech choices can create irreversible problems later in the project.

The core of Agentic Workflow is breaking this vicious cycle.

Today, whether it's Antigravity or GitHub Copilot, next-generation AI development tools have embraced AI Agents and Planning as core concepts. This represents a fundamental shift in development philosophy and methodology.

The New Workflow: Communicate, Confirm, Discuss

In this new workflow, you don't rush to write code. You start with a deep dialogue with the AI Agent:

  1. Communicate: Clearly describe your vision and specific requirements.
  2. Confirm: Have the Agent restate and verify it correctly understands your goals.
  3. Discuss: Dive deep into system architecture and implementation details, identifying potential risks and issues upfront.

Only after Communicate, Confirm, and Discuss do you move to implementation. This plan-first-then-execute strategy avoids the inefficient cycle of writing, revising, and deleting.

Case Studies: From Concept to Reality

Here are three recent projects that demonstrate how Agentic Workflow works in real-world scenarios.

Project 1: Infinite Taiwan

Demo: Infinite Taiwan

This is an element-merging game centered around iconic Taiwanese elements like "Bubble Tea," "TSMC," and "Night Markets."

My initial concept was to create a Taiwan-themed version of Doodle God or Infinite Craft. With basic frontend and backend knowledge, you can quickly build a working prototype.

I used Vite + React as my standard tech stack, starting from the official project template with Tailwind CSS v4 and TypeScript to rapidly scaffold the initial architecture. Through iterative development, I continuously communicated with the Agent to optimize various details.

To squeeze a bit more runtime performance out of it, I eventually migrated the project to Preact (a lightweight React alternative) and integrated VitePWA for progressive web app (PWA) caching. For image loading experience, after discussing with the Agent, I adopted low quality image placeholder (LQIP) techniques. This kept the development rhythm sharp and efficient.

The most time-consuming part was actually generating image and music assets. For this, I primarily used Gemini or ChatGPT for content refinement and AI music tools like Suno for composition.

For image processing, I tried vector conversion with Illustrator, but the exported SVG files were often too large and complex. I stuck with WebP format for static asset compilation and optimization, balancing quality and load performance.

I'm currently refining the game mechanics and gameplay, with potential future additions like multi-language support.

Project 2: Taiwan DNS Checker

Demo: DNS Block Check Tool

In a previous article, Taiwan's DNS RPZ Network: Blocking and Unblocking Strategies, I explored topics related to Taiwan's Response Policy Zones. While I use my own self-hosted DNS server and am unaffected by blocking, a thought occurred to me: if I wanted to build a public query tool, how would I implement it?

Since it involves DNS queries, a backend service is essential. I'm familiar with Cloudflare Workers, so I decided to use this serverless computing service for the query logic. But I also wanted to log query history for analytics. This requires a database. I wasn't sure if I needed to go through the trouble of self-hosting PostgreSQL, or if there was a lighter solution better suited for serverless architecture.

So during the Planning phase, I presented the following prompt to the Agent:

I want to develop an ultra-lightweight web frontend for a "Taiwan DNS Block Check Tool."

Core requirements:
1. User inputs a domain name, frontend sends request to Cloudflare Workers backend.
2. Worker executes DNS Query (against 101.101.101.101:53).
3. Logic: If the resolved IP is 150.242.101.120, the domain has been DNS hijacked; otherwise, it's normal.
4. Logging: Regardless of the result, the backend must record each query.

Goals:
- Build query statistics.
- Frontend displays "Popular Queries" and "Top Blocked Domains" rankings.
- Provide a tutorial guiding users to switch their DNS to 1.1.1.1 or 8.8.8.8.

Technical concerns:
I'm unsure about best practices for backend data logging. Do I still need to self-host PostgreSQL? Would the maintenance cost be too high? Is there a lighter, more serverless-friendly alternative?

After analysis, the Agent pointed out that for lightweight applications like this, self-hosting PostgreSQL isn't necessary. It recommended Cloudflare D1 (a distributed database service based on SQLite) as an alternative, which integrates with Workers to form a complete serverless stack.

This gave the project:

  • Zero maintenance overhead: Fully managed by Cloudflare. No database setup or maintenance headaches.
  • Native integration: Deep integration with Workers, so development goes smoothly and performance holds up.
  • Generous free tier: 5 million rows read and 100K rows written per day, plenty for personal projects.

That is where the Planning phase pays off. Determine direction before implementation. Without this step, I might still be struggling with PostgreSQL environment setup. With Agent guidance, I finalized the most efficient solution within minutes.

During implementation, there were minor hiccups (like timezone display errors and expanding blocked IP detection logic), but quick dialogue resolved them rapidly.

For me, the biggest takeaway from this project was rapidly learning and adopting new tools like Cloudflare D1 and KV within limited time. This added another option to my toolkit for future project evaluations.

The page also includes a DNS Setup Tutorial. Looking back at the entire development process, the biggest challenge was actually image processing, not the frontend layout itself.

Project 3: GemTube

This is a browser extension designed to optimize the Gemini user experience: GemTube.

My previous development habit was writing userscripts for various small tools. But when sharing them, I realized this was extremely unfriendly for end users: they had to install Tampermonkey first, and even understand how to install custom JS files. The steps are quite tedious.

Through Planning + Agent, I was able to quickly consolidate several scattered scripts into a proper extension focused on improving how Gemini and YouTube work together.

During GemTube development, I addressed several clear pain points:

  1. Lack of convenient search engine integration:

    In a previous article, Replacing Google with ChatGPT Search and Setting Up Temporary Chats by Default, I explained how to add ChatGPT as a browser search engine using URL parameters with temporary chat enabled by default.

    However, Gemini currently doesn't offer similar URL parameter mechanisms. You can't directly specify which model to use via URL either. I wanted to bring the same convenient experience to Gemini.

  2. Overly cumbersome video summarization workflow:

    In another article, Using ChatGPT for YouTube Video Analysis and Summarization, I shared a script-based method for quickly extracting video transcripts.

    While that solution solved transcript extraction, you still had to manually copy-paste text into GPT for analysis.

    Gemini's backend already integrates directly with YouTube: paste a video URL and it analyzes the content without a transcript step in between. But I still wanted to automate the flow from "copy URL" to "open Gemini for analysis."

  3. Insufficient URL parameter support:

    Gemini natively doesn't support URL parameters (like ?q=...) for auto-filling the chat box and submitting queries, let alone auto-switching models.

To solve these pain points, I consolidated multiple standalone scripts into GemTube. This tool enables automation and provides a complete settings page for users to customize behavior.

Here are GemTube's core features and settings details:

  1. Gemini URL Parameter Automation This is the tool's signature feature, giving Gemini the URL control capabilities it originally lacked. Users can achieve the following via specific parameters:

    FunctionURL Parameter Example
    Auto-fill text only (draft mode)?q=Hello+World
    Auto-fill and immediately send?q=Hello+World&send=true
    Switch to specific model and fill text?q=Analyze+this&model=2 (e.g., Gemini Advanced)
    Temporary chat + Model 2 + Auto-send?q=Code+review&model=2&temporary-chat=true&send=true
    Enable temporary chat only (no text)?temporary-chat=true

  2. YouTube Video Analysis Enhancement For YouTube viewing, the extension offers deeply integrated analysis features:

    • ✨ Quick Analysis Button: Displays a button below the video. Click to automatically capture info and send to Gemini for parsing.
    • Custom Analysis Prompt: Users can preset prompts like "Provide a detailed summary and analysis of the entire video content" for consistent analysis results.
    • 📋 Quick Subtitle & Comment Copy: When enabled, pressing Ctrl+C without selecting text automatically grabs video subtitles or comments and appends preset prompts (e.g., requesting Traditional Chinese output, detailed transcript digestion).

Agent-Assisted Implementation Process

Since I had no prior experience developing Chrome extensions—only simple userscripts—I provided my completed scripts directly to the Agent and asked it to help with project initialization and architecture conversion.

During the process, I observed that the Agent first auto-generated manifest.json (extension declaration file) and set up corresponding host_permissions, content_scripts, options_ui, and other configurations. These tedious steps that typically require consulting Google's extension documentation were completed and converted in minimal time.

Conclusion

Combining AI Agents with a planning step is where software development is heading. Planning first and implementing second lowers the technical barrier a lot, and it puts the project on the right architecture from the beginning. That is what saves you from finding out halfway through that the direction was wrong from the start, which is where projects get hard to finish or die outright.

In practice, don't over-rely on a single model. Different models have different strengths. Sometimes a logical bottleneck that Model A can't crack dissolves instantly when you switch models.
